# CLAUDE.md: working rules for Claude Code in this repository

## Source of truth
- README.md and the files in its Documentation map are the source of truth for scope, architecture, source-of-truth rules, roles, features, KPIs, roadmap, Decision log (docs/decisions.md) and Open decisions (docs/open-decisions.md). Read README.md first, then the files the task touches; refer to sections by name. Treat decisions as settled unless asked to reopen one.
- docs/definitions.md defines every term, label and metric word: every UI label, column header, hint, API field, setting, SQL name and catalog entry uses its terms in its meaning. A new term or a changed meaning updates docs/definitions.md in the same PR, with a docs/decisions.md row starting 'Definitions:'. A retired word is never introduced.
- docs/RUNBOOK.md describes how changes are built, merged, released and verified.
- web/CLAUDE.md and web/AGENTS.md hold the Next.js rules for web/. Read them before touching web/.
- Write everything in English: code, comments, SQL, docs, commit messages and PR descriptions.

## Style
- docs/style/Pulse4all-Style.md is the style of everything the CMA shows. Every UI change follows it: colours, type, components (7.1 to 7.8) and tone of voice for copy.
- Where two rules meet, the more specific wins. Where it says nothing, derive the choice from it and name it in the PR; never pick freely.

## Principles
1. Configurable, not tailor-made: markets, skills, statuses, thresholds, SLAs and rules are tenant configuration or seed data, never code. Nothing Pulse4all- or vendor-specific is hardcoded; vendors sit behind adapters.
2. Multi-tenant and role-based from the first line: every table is tenant-aware (`cma.setup_tenant_table()` for RLS, grants and audit), every query and route respects role permissions.
3. Open: data is reachable through the API (`/api/v1/...`).
4. Step by step: the smallest working version, but the clean option over the shortcut.
5. One source of truth per data type (README, Source of truth). Postgres mirrors the owning system and never overrules it. HubSpot stays the CRM; never propose moving CMA features into HubSpot.
6. Data first: flag when a feature or metric depends on a HubSpot or Aircall data prerequisite that is not in place.
- The CMA UI shows no customer data: ids, statuses and links to HubSpot or Aircall only.
- Flag anything that weakens configurability, tenant separation, security, data protection or the source-of-truth rules.

## Git and release
- Never push to main; it only accepts pull requests (repository ruleset). Work on a branch, open a PR, never merge it yourself. Martin reviews and squash-merges.
- A merge to main that touches web/** or cloudbuild.yaml builds and deploys PROD (Cloud Build trigger cma-web-main). README, db/, docs/ and records/ do not build.
- One increment per PR, small and reviewable. The PR description states what changed, why, how it was checked, and what Martin still has to run.
- In this session, run in web/: `npm ci`, `npm run build`, `npm run typecheck`, `npm run lint`, and the pure verifiers (`npm run verify:copy`, `verify:corrections`, `verify:csv`, `verify:dashboard`, `verify:live`, `verify:team`, `verify:roster`, `verify:configuration`, `verify:messages`, `verify:import`, `verify:devices-import`, `verify:datamap`, `verify:signed-out`, `verify:invitations`, `verify:preview`, `verify:follow-up`, `verify:reports`, `verify:flash`, `verify:period`, `verify:health`, `verify:boundaries`, `verify:jobs`, `verify:metrics`, `verify:cache`, `verify:function-bases`). Report the results in the PR. Verifiers that need a server or a database (`verify:api`, `verify:theme`, `verify:layout`, `verify:hints`, `verify:iap`, `verify:scheduler`, `verify:round-trips`, `verify:refresh-follow-up`, `verify:perf`) and every db/ script are run by Martin in his own terminal or Cloud SQL Studio.
- records/ holds outputs of real runs only. Write a record only when Martin supplies the values from his own runs (ids, counts, times; no keys, secrets or personal data), and say in it that it was written down from his report, as in PRs #120 and #121. Never invent a value, alter what a record already says, or backdate one; a later run is added as its own section or record.
- Raw outputs from prod are never committed or pushed before `node tools/check-records.mjs records/<dir>` passes; a prod output that fails it is masked first (the operator's login as `<operator>`), or its rows are left out with one line saying why, as 0009g's prod 07 did. The repository is public until launch.
- Never change cloudbuild.yaml substitutions or environment variables without saying so explicitly in the PR.

## Subagents
- .claude/agents/ holds the project subagents: cma-reviewer, cma-db-reviewer, cma-security-reviewer, cma-performance, cma-migration-impact and cma-advisor (all read-only), and cma-docs-keeper. cma-db-reviewer applies when db/ changes, cma-security-reviewer when web/, ingest/ or db/ change, cma-performance when web/ or db/ change (it proposes gains and flags a slower page; it decides nothing), cma-migration-impact before a migration that re-creates a function or changes a table, view or column (it lists the verifies to rerun), and cma-advisor at the start of a brief or on request (what may be forgotten, adjacent opportunities; it is not part of the review chain). They start without this conversation, so the delegation message carries the brief's goal, the decisions made (verbatim), the migration number and the verifier results.
- Every brief that changes code ends in this order: build and run the pure verifiers; delegate to cma-reviewer and, in the same message, to the specialised reviewers that apply; fix every Critical, re-run the verifiers and review once more at most; a Critical still open after the second round goes in the PR description as open, never fixed silently; delegate to cma-docs-keeper with the reviewers' verdicts; open the PR with cma-reviewer's three-line summary, the specialised reviewers' one-liners and the performance opportunities taken or left and the docs keeper's file list.
- A docs-only change skips the reviewers. A brief can say "no subagents" for a trivial change.
- Subagents never run db/ scripts, never write records/, never reach a database or Google Cloud, and never use connectors.
- .claude/settings.json wires hooks (`.claude/hooks/guard.mjs`, unit test `guard.test.mjs`) that enforce what the harness can check: no push to main, no `gh pr merge` or merge through the GitHub tools, a commit or push carrying records/ files runs `tools/check-records.mjs` first, and a reminder when `cloudbuild.yaml` or an existing db/ script is edited. A blocked call is never worked around.
- .claude/skills/ holds the procedures: `new-migration` (numbers, script frame, verify, budgets, docs, Martin's steps) and `pr-description` (the PR's required shape); use them when a brief adds a migration or a PR is asked for.

## Database (db/)
- Scripts are numbered and run in order; a change is a new script plus its verify script (for example `32_<name>.sql` and `33_verify_<name>.sql`), not an edit to a script that has run in prod. Every new tenant table gets `cma.setup_tenant_table(table)`.
- A migration that redefines a function (a `create or replace` of the same schema, name and argument types, or a drop and create under the same name, also with other argument types) starts from that function's latest earlier definition in run order, whatever script holds it, and carries `-- based on: <file>.sql` on the line directly above the `create`, naming that script (from `152` on; `verify:function-bases` enforces it). Its verify compares a rewrite meant to keep the answers with that latest definition, and a change that puts back a rule the function lost with the definition that held the rule (`153` against `100`).
- A migration that re-creates a function reruns every verify that reads it, directly (`grep -lw 'cma\.<function>' db/*verify*.sql`) or through the functions that call it: its header and the PR's steps name them, and a verify the change alters is said to be edited by it.
- Follow the conventions in docs/architecture/data-model/ and docs/architecture/api.md: error codes, permissions, the provoke switch in verify scripts.
- A PR that adds or changes a table, view or column in cma or cma_read updates docs/datamap/catalog.json (a `what` and `how` for each new table, an entry for each new computed view) and says in its description that Martin refreshes docs/datamap/schema.json from dev on this branch after running the migration there, before merging; until then verify:datamap fails on this branch, which is expected. A change to how or how often a source fills a table (webhooks, job schedules, catalogs) updates that table's `how` in the same PR. A PR that changes docs/datamap/index.html ends its description with: After merge: in the Claude project, say "republish the data map".

## Performance
- Targets (Decision log, 5 November 2026, night N06; to confirm): a click shows something within 100 ms (a route skeleton, a pending state or the optimistic result); server time to first byte p75 ≤ 150 ms and p95 ≤ 400 ms on the agent pages and the Live board, p75 ≤ 400 ms and p95 ≤ 1,000 ms on report pages, Flash, Sources, System health and Data quality; a poll ≤ 20 ms of database time in one transaction; at three times prod's volume a list's first page ≤ 300 ms, an overview or landing ≤ 500 ms, Sources ≤ 150 ms, Data quality ≤ 500 ms on stored results. The budgets files: `db/131_time_all.sql` (the database reads per page, poll and report; `124` keeps Flash's own), `web/verify/round-trips.json` (transactions and statements per request), `web/verify/perf.json` (time to first byte per route class, HTML and JavaScript per route). The prod truth is the request log line (`totalMs` per `route`): `tools/perf/request-percentiles.mjs` turns `gcloud logging read` into p50, p75, p95 per route.
- A new read comes with its row in `131_time_all.sql` and its budget in `round-trips.json` (a page that gains a transaction fails `verify:round-trips`, which is the review's question); a page that gains client JavaScript or payload is checked against `perf.json`.
- A new index on a busy table (`ingest_event`, `sync_run`, `subscription_event`, `crm_record`, `telephony_call`, `commerce_order`, `crm_call`, `commerce_customer`) is created concurrently from the Terminal, outside a transaction (`create index concurrently if not exists`, one statement each, `lock_timeout` and `statement_timeout` per statement, `pg_index.indisvalid` checked after), never inside a migration's transaction and never from Studio, which wraps a script in a transaction. A constraint or other ACCESS EXCLUSIVE change on a busy table goes last in a migration's transaction, directly before the `schema_migration` insert and the commit: the lock is held until the commit, so everything that follows it in the script makes every reader and writer of the table wait (`132_perf.sql`, section 10).
- Measure first, on `web/verify/perf-volume-fixture.sql` (three times prod's volume, local only), and prove equality: a rewritten read keeps its previous definition inside its verify script and compares the two row for row (`133_verify_perf.sql`'s pattern), provoked by a deliberate difference. Lessons of night N06 (backlog CMA-084's rule): under the application role the planner is planned with parameters, so a one-row settings relation joined with `cross join s` ends up inside a per-row loop (use scalar subqueries `(select s.x from s)`); `exists()` over a big table is planned as a scan expected to stop at once and reads the whole table when there is no row (use `min(<leading indexed column>) is not null`); a SQL function inlined into its caller takes the caller's expressions as bounds, which can cost the index (a configuration setting such as `set jit = off` stops the inlining, and a later `create or replace` drops it: the script that recreates the function repeats the alter); an aggregate inside a plpgsql `select into` may run in parallel, a `return query` (a cursor) may not; an ordered aggregate (`array_agg(... order by)`) sorts its whole input; a view that groups or windows the history cannot take a caller's bound (a grouped view takes one only through its grouping columns, a windowed one only through its partition columns, and a join on a computed value never reaches either): compute the day in a function called per row and keep the view a plain scan with a lateral call, which no plan can turn into one pass over the history (`134_hours_reads.sql`); a function inside a view runs with the caller's rights (the readers of `cma_read` hold none on the tables and need an owner's-rights wrapper of their own, which the planner never inlines: keep it off the application's path), and a set-returning function says its `rows` (the default of 1,000 costs a read into JIT, 700 ms on a session's first call); a plpgsql function's statements turn to the generic plan after five calls on a connection, and the pool keeps its connections, so measure the seventh call of a session too (the generic plan took `cma.team_hours` from 12 to 440 ms before N06d).
- No cache across requests holds a report, a person's data, an inbox or anything under a per-user permission check; a tenant-scoped catalog may be cached per instance for a short time (`src/lib/cache-core.ts`, `CMA_CACHE_TTL_MS`), keyed by the tenant and, where the answer depends on it, the permission set, and invalidated by the write paths that change it (`verify:cache` proves two tenants and two roles never see each other's entry).

## Ingest (ingest/, docs/ingest/)
- No ingest route takes personal data in its path or query string: the path holds the adapter and the connection key (an identifier, not a secret), secrets travel in headers or signatures, data in the body. Cloud Run's request log keeps the URL (Decision log, 12 October 2026).

## Security and data
- No secrets, tokens, passwords or connection strings in code, commits, PR descriptions or setup scripts.
- No real personal or customer data in code, fixtures or tests; use the dev seed.
- Authentication follows README (Authentication): Pulse4all signs in with Google Workspace through IAP; the app verifies IAP's signed token on every request and matches people on their external id, never on email. Never trust plain identity headers or weaken this check; mock identities exist in dev only.

## Instructions for Martin
- Every command block in a PR description or reply is labelled with where it runs: **Studio** (SQL in Cloud SQL Studio, naming the instance cma-dev-pg or cma-prod-pg), **Terminal** (Martin's own Linux terminal: Chromebook Linux or his Linux machine, in ~/cma unless stated), **Browser** (a page or click path) or **File** (a repository path). Never mix SQL and shell in one block. A query that returns customer rows is a Studio block, never Terminal (README, Where a command runs).
- Give one step at a time and state the expected output.
- When a decision is made or something changes, update in the same PR: a row in docs/decisions.md (at most two sentences, naming the PR), the affected sections in whichever file holds them, and one dated line at the top of CHANGELOG.md. Reference sections get no history (counts over time, earlier values, records paths): that belongs in records/, CHANGELOG.md or the PR. Keep README.md under 80 KB.
