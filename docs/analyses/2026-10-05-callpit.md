# Callpit analysis: callpit.netlify.app and what the CMA can take from it

Oct 5, 2026 · @Martin

## Summary

Callpit is the Invest agent cockpit from the AgentUI project: a parity rebuild of the Steam Connect agent screen, live at `callpit.netlify.app` without a login, running on mock data. It is a different kind of product from the time-and-status demo: it is where an agent works a customer record, dials, books a result code and moves to the next task. The README parks Callpit and keeps customer data and post-call outcome logging out of the CMA, so "embedding elements" means taking patterns, integration mechanics and configuration shapes, not screens.

What is there: a 24-field lead form, an 11-button grid with keyboard shortcuts, a result-code catalog of 16 codes with outcomes, ceilings and "what is still needed to book" rules, a two-step callback picker with ISO weeks and 10-minute slots, an embedded Aircall softphone with a call-phase state machine, an incoming-call screen pop, a read-only search that never steals the task, a memo history, a queue counter with period filter, and three tools (script and Q&A, email with a compliance notice, evaluation form). The platform handover in this project documents the engine behind it (queue models, `fn_book_disposition`, leasing, outbox) in depth; this analysis confirms what the deployed build does and maps it to the CMA.

The verdict:

- Take into the CMA: the keyboard-first discipline, the Aircall call-phase model as the source for on-call time and talk time, the queue counter as the shape of the speed-to-lead and open-work widgets, the incoming-call pop reduced to status and a CRM link, the "needed to book" pattern as configurable requirement flags, and the result-code catalog as the vocabulary for outcome metrics once synced
- Leave in the cockpit, or in HubSpot: the customer form, deep links to customer records, dispositions, memo, callbacks, scripts and emails. These are the agent's customer work, which the README places in HubSpot and Aircall
- Resolve before any of it is built: whether the cockpit comes back as a product beside the CMA. If it does, tasks and dispositions get a second system of record (the handover says Postgres owns the queue; the README says HubSpot owns leads and deals), and the Source of truth section has to say which

Separately from the CMA: the site is public, posts form data to a Make webhook whose URL is in the bundle, and shows the Steam palette rather than the Pulse4all style. All three are known from the handover and fine for a mock, none is fine for real investor data.

## How this was done

The deployed build is a Next.js client bundle, so the analysis combines a read of the beautified bundle with a headless walkthrough, cross-checked against the platform handover already in this project. Steps, 5 October 2026 around 22:00 CEST:

1. Fetched the page: a Next.js app, `lang="nl"`, title "CRM Pulse4all - Agent", description "P4A Call Center Agent UI - Invest PoC", `noindex`
2. Downloaded and beautified the page chunk (94 KB, 4,186 lines) and read the configuration objects: option lists, the 16 result codes, the 11 buttons, the two campaign configs, the mock task, the mock agents, the Aircall controller, the availability controller, the disposition hook, the keyboard handler, the queue widget, the tools
3. Rendered the screen in headless Chromium at 1440 and 1920 px wide; opened the queue dropdown, memo history, the three tools, search (F2), the callback picker (key 4), the completion dialog (key 8), and simulated an incoming call through the test hook that `?p4atest` enables
4. Probed the API routes: `/api/search`, `/api/next-task` and `/api/lookup-by-number` answer with mock data; `/api/queue` does not exist
5. Compared findings with the handover sections Data model and queue engine, Invest Agent UI, Aircall integration and Deployment state

Nothing was booked. The disposition buttons were pressed only as far as their dialogs; no commit, no email, no webhook call. The Aircall softphone was not signed in. All names, numbers and addresses on the screen are the bundle's mock data (Johan de Vries, example.nl, a Rotterdam address).

**Rules the screen upholds**

- Phone numbers are normalised to E.164 before anything; an implausible number blocks booking with a plain message
- A record opened from search is out of the queue and cannot be booked; the agent's own task is kept and restored on close ("Terug bij je eigen taak")
- Only one booking at a time (a ref guards double presses); the console logs the full disposition payload with task id, code, callback moment, field diff, client timestamp, memo and agent
- The memo prefix is stripped before the memo is judged empty, so a code that requires a memo cannot be satisfied by the prefill
- The deal dialog explains itself: "Een deal zonder bedrag is niet te rapporteren, en dat is de reden om hem vast te leggen"
- After booking, a flash confirms "Afgeboekt – 500 Terugbellen" and the next task loads; in this build the next task is the same mock with a new id

**Callback picker.** Two steps: a month calendar with ISO week numbers and today outlined, then slots on the right split into day (8:00–21:50) and night (22:00–7:50) in 10-minute steps; a footer shows the chosen moment or "Nog geen moment gekozen"; Vastleggen is the booking. Escape cancels, Enter confirms.

For the CMA this catalog matters as reporting vocabulary, not as a screen: outcome metrics (conversion, reasons for not buying, attempts per lead, the hard cap of six) are defined on these codes, wherever they end up being booked.

## Aircall Everywhere findings

The cockpit's Aircall layer is the most directly reusable piece for the CMA, because the CMA's live view and productivity metrics need exactly this: who is on a call right now, for how long, and what counts as talk time. Everything here was measured against the real SDK by the AgentUI project and is confirmed by the bundle.

| Finding | Detail | Consequence for the CMA |
| --- | --- | --- |
| Two commands only | `dial_number` (fills the dialpad, does not connect) and `exit_keyboard`; no mute, hold or hangup through the SDK | The CMA never drives calls; it observes them |
| Events | `incoming_call` (call\_id, from, to), `call_end_ringtone` (answer\_status), `outgoing_call` (call\_id, to), `outgoing_answered`, `call_ended` | A client-side phase model: idle → dialing or ringing → on-call → wrap-up |
| Login state | `onLogin` with the user's email, `onLogout`; `isLoggedIn` returns a `(success, data)` pair, not a boolean | The agent's Aircall identity is known in the browser and matches `app_user_external_id` (`aircall_user`) |
| Iframe | 376 × 600, never unmounted or `display:none`, moved off-viewport instead | Any CMA screen that hosts the softphone keeps it mounted all day |
| Client events are unreliable | `call_ended` is lost when a laptop closes; webhooks are the only reliable record, and `call.ended` arrives about 30 seconds late | Postgres takes call facts from the Aircall sync (README: Source of truth); the browser phase is a live hint, never the record |
| Talk time | `ended_at − answered_at`; Aircall's `duration` includes ring time | Define productivity on talk time, not duration |
| Join key | numeric `call_id` in both SDK events and webhooks | The key between an Aircall call and a CMA status interval or lead assignment |
| Availability | Aircall owns pause and availability once the screen drops its own Pauze button; whether availability is readable through the API is open | The CMA's statuses and Aircall's availability are two states until a sync or a rule ties them |
| Inbound | Aircall owns IVR, queue and routing; `to` tells which number, and so which proposition, was called | The incoming-call pop in the CMA can show status, number called and a CRM link, nothing more |

**The availability controller in the bundle** (`agent-state.ts`) holds `availability` (available, pause, offline), a `pendingPause` flag that applies the pause after the current call ends, `shiftStatus` ("Niet ingedeeld op dienst") and `onShift`. It is an interface with no backend yet. This is the hinge between the two products: the CMA's `work_status` is the agent's declared state, Aircall's availability is the phone's state, and the "pause after this call" behaviour is the one the CMA should offer when an agent picks Break mid-call.

**Formatting helper worth lifting.** The number formatter renders Dutch numbers for reading (`06 12345678`, `020 8080890`) from E.164 and keeps E.164 for everything else, with the Dutch area-code set built in. Small, tested, and the CMA's Live board will show numbers for inbound calls.

Two cockpit decisions are worth copying into the CMA's own rules even though the features differ: the screen payload is a view and never a schema (no lease, priority or raw counters reach the browser), and actions never block on an integration (the agent only ever sees a failed dial). The CMA's outbox and the "nothing awaits Make, HubSpot or Aircall in the render path" rule are the same principle.

## Conflicts with the README and risks

The cockpit and the CMA are complementary products, and the README has already drawn the line between them; the risk is in blurring it.

**Where the README stands** (sections Out of scope, Source of truth, Why standalone)

- Callpit is parked and the CMA starts fresh
- Customer data in the UI is out of scope: the CMA steers people, customer work happens in HubSpot and Aircall
- Post-call outcome logging is out of scope: handled in HubSpot and Aircall
- HubSpot is the source of truth for leads, deals, tickets and owners; Postgres mirrors and never overrules

**The one real conflict.** The handover's first rule is "Postgres owns the queue, never the CRM", with dispositions, attempts and callbacks as facts in the cockpit's own database and HubSpot receiving a coarse engagement. The README's rule is the opposite for leads and deals. Both are right for their product, and they are compatible only if the Source of truth table gets a row for *tasks, attempts and dispositions* that names an owner. Three possible owners: HubSpot (the cockpit writes result codes to a custom property and the task list is a HubSpot queue), the cockpit's queue engine (a second system the CMA syncs from, like Aircall), or the CMA itself (the cockpit becomes a module of it, which the standalone decision and the no-customer-data rule argue against). This is the decision that gates every reuse in the previous section.

**Risks in the deployed demo**, known from the handover and confirmed here, listed because the site is public:

- No login and no password on `callpit.netlify.app`; today it holds only mock data, so this is harmless until the day it does not
- The email processors and the form post personal data to a Make webhook from the browser; the webhook URL is in the public bundle, so anyone can post to it; nothing is audited and a failed post is silently lost. The handover already requires this to move behind the outbox before production
- Steam palette, Dutch copy and 1920 × 1080 no-scroll are deliberate parity choices for the Invest line; none of it applies to the CMA, which follows Pulse4all-Style.md and the dense scale (decision 5 October)
- `call_ended` from the browser is not a record; any CMA metric that counted on it would miss closed laptops
- The Investors tab is provisional and codes 900 to 902 have no screen of their own yet

**Data protection.** The cockpit shows investor names, addresses, amounts and objections; the CMA deliberately shows none of that. If any cockpit element moves into the CMA, the no-customer-data rule has to hold for it (the incoming-call pop and the queue counter in the previous section are written to that rule). Investor communication from the email tool is AFM-supervised and goes through the p4a-compliance check; that stays with the cockpit.
