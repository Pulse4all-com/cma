# API: the web app's data layer

Part of the CMA documentation (README.md, Documentation map). Moved verbatim from README.md on 20 October 2026.

### API: the web app's data layer (since 5 October 2026)

The web app reads and writes Postgres **in-process**: screens and route handlers call `data()` from `src/lib/data`, which returns the Postgres implementation when `CMA_DATA_MODE=api` and the in-memory mock otherwise. There is no HTTP hop between the screens and the database. The ingest API for Make and n8n (Roadmap step 3) is a separate Cloud Run service with its own service account and per-tenant keys; it can lift `src/lib/db/client.ts`.

**Rules in every call.** One transaction per call with `app.tenant_id`, `app.user_id` and `app.actor_label` set by `set_config(…, true)`, so a pooled connection can never carry one request's tenant into the next. Own data only through the database: every read filters on `cma.current_user_id()`, the transaction's acting user, never on an id passed in. The database clock decides: `open_workday()`, `set_status()` and `end_workday()` are called without a time. Today is the business date in the user's zone, computed in SQL. Minutes on screen are working seconds rounded down per day (which hours the agent sees stays open, see Open decisions). Errors keep their SQLSTATE; SQL text never reaches a screen. `GET /api/health` is the only route outside `/api/v1`: liveness for Cloud Run and the deploy's smoke test, `{ status, version, auth, data }`, no user data, not gated by `proxy.ts` (IAP in front of the load balancer still gates it).

**Login (`findPrincipal`).** `cma.find_tenants_for_identity(provider, subject)` without a tenant; exactly one tenant continues, none or several (no tenant picker yet) is "no access yet". Inside that tenant the `app_user` row, its employer, its zone (`cma.user_timezone`), its role and, since 6 October 2026, its permission keys (`cma.user_permissions`) for showing or hiding screens: screens check a permission, never a role key, and the database checks again on every call. A user without a role is "no access yet". With several roles the earliest grant is shown, without ranking role names. A database that cannot be reached is an error, never "no access".

**JSON API**, versioned, behind the same gate and identity as the screens, no tenant parameter anywhere and no user parameter on the `/me` routes, `cache-control: no-store`:
