The 4 connections `cloudsqladmin` (Cloud SQL's own superuser) held on 15 October 2026 therefore leave 93 in practice, and the ceilings fit with 5 to spare (10 without the BigQuery reserve). Raising `max_connections` is rejected for now (Decision log, 15 October 2026). Cloud Scheduler starts the sweep, the form poll and the email poll every minute whether or not the previous execution has finished (task timeout 10 minutes), so a run longer than a minute overlapped the next one: in the worst case ten of each at once, 3 × 10 × 3 = 90 more, which would have passed the limit (88 + 90 = 178). ### Release flow: sandbox to production in small steps

- Dev is the sandbox, prod is live. Every increment that works and is verified in dev is promoted to prod; dev then moves on to the next iteration. Production exists from the first increment (migration 0001). We do not build the whole platform first and launch at the end.
- An increment ships with its migration, its verify script and a short release note. Promotion to prod: confirm point-in-time recovery is on (or take an on-demand backup), run the migration as `cma_owner` under a personal login, run the verify script, keep its output, then release the matching application or sync change.
- The verify output (screenshots or exported results) is kept per environment and date, for example `records/0002-dev-2026-10-05` and `records/0002-prod-2026-10-05` (migration 0001 ran on 4 October 2026 before `records/` existed), next to the scripts in the repository. Records and the README pass of an increment are committed before the next increment starts and checked in the repository (`ls records/`, `git log -- README.md`), not assumed from a PR title. A verdict that never reached `records/` is rerun and recorded under the date it actually ran, never backdated (7 October 2026: the 0003b verdicts and the README's seventh and eighth passes had not reached the repository).
- The schema snapshot `docs/datamap/schema.json` is refreshed from dev and the data map rebuilt (`node tools/datamap/build.mjs`, then `--check`) on the increment's branch, after its migration and verify ran in dev and before the merge, so main always passes `verify:datamap` (`docs/datamap/README.md`); the same branch adds its tables and views to `docs/datamap/catalog.json` (CLAUDE.md, Database). After the merge, the page is republished to its one link when `index.html` changed (`docs/datamap/README.md`, Publishing).
- With a web change (since 6 October 2026, because only prod's build makes images): migration and its verify script in dev, then in prod, then the merge to `main` (which builds and deploys prod), then the same image on dev by its short SHA for the API verifier and its `--provoke` run, then a hand check in prod. A migration therefore never breaks the web app already running, and a web change keeps working on the database it meets. A web change without a migration starts at the merge (c2.1).
- Migrations are forward-only and rerunnable. A mistake is fixed with a new migration, never by editing one that has shipped. Should a business line ever get its own database, the same migration runs there too.
- Prod holds real data from the first agent hours onward, dev never. Test data for a new feature lives in dev; a feature is only done when it is verified in prod.
- A verification is not verified until it has been made to fail on purpose (every verifier has a `--provoke` mode). Inherited from the AgentUI trial.
- Every commit reaches `main` through a pull request, the records and README passes of an increment included (repository rule since before 7 October 2026; the API records of increment f were refused as a direct push and merged as PR #38). During a GitHub incident the merge can land without the webhook that starts the build: `gcloud builds list` then lacks the SHA and `gcloud builds triggers run cma-web-main --sha=<full sha>` starts it by hand (7 October 2026); a late delivery that builds the same SHA again is harmless. The build appears 2 to 4 minutes after the merge (3.5 minutes on 14 October 2026), so the check waits 4 minutes before the trigger is run by hand: a manual run next to a late automatic one deploys the same image twice, which is harmless but needless (Decision log, 14 October 2026). After every merge that touches `web/**` or `cloudbuild.yaml`, confirm with `gcloud builds list --project=p4a-cma-prod --region=europe-west4 --limit=1` that a build exists for the merge's short SHA, because a trigger that cannot create a build leaves no trace in the build list (11 October 2026).
