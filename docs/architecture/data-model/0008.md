### Data model: messaging core and record alerts (migration 0008)

Written on 10 October 2026 as intake track I6 from `docs/night-2026-10-10/DESIGN.md` §4.5 and §8 (brief B5). Run and verified locally on PostgreSQL 18.4: `42_messaging.sql` twice, and `43_verify_messaging.sql` passing normally and failing under provoke. Sixteen mutations were caught and every earlier verify was unchanged; the outputs are in `docs/night-2026-10-10/local-records/0008/`. Run in dev and prod on 10 October 2026 (`records/0008-dev-2026-10-10`, `records/0008-prod-2026-10-10`). Universal: rules, audiences and links are tenant configuration. Messages carry references only (README Messaging): an alert's title and body are built from configuration (`New deal`, then `<market> · <pipeline label> · created <local time>`), never from customer data.

| Table | Scope | Holds |
|---|---|---|
| `message_rule` | tenant | which created records raise an alert for whom: name (the identity), trigger `record_created`, record type, pipeline ids (empty: every counted pipeline), audience permission (default `leads.accept`), `match_language`, `only_clocked_in`, fallback permission (default `leads.manage`, null for none), urgency, enabled, `max_age_minutes` (null: the setting `alerts.max_age_minutes`); disabled, never deleted |
| `message` | tenant | an alert or an announcement: urgency, title (≤ 120), body (≤ 500), the record it points to (`ref_system` the adapter, `ref_type`, `ref_id`, `ref_url` https only), the rule, the target as asked (for an alert, the rule's terms, the market and whether the fallback was used), sender, `created_at`, `expires_at`. Append-only; one alert per rule and record (unique index), so a retry writes nothing |
| `message_delivery` | tenant | one row per recipient, resolved when the message is written (history stays exact when teams or skills change): `delivered_at` (the recipient's first poll that returned it), `read_at`, `acknowledged_at`. Each time is set once and never moves (trigger); read implies delivered, acknowledged implies read |

| Function | Does |
|---|---|
| `cma.upsert_message_rule(name, record type, pipeline ids, audience, match language, only clocked in, fallback, urgency, max age?)`, `set_message_rule_enabled()` | configuration for `tenant.configure` |
| `cma.ingest_record_alerts(connection, record type, source ids)` | the ingest service's call after a read-back of created records (`ingest.write`, at most 500 ids). Each record (not deleted, younger than the age limit) meets each enabled rule of its type whose pipelines it is in. The recipients are active people holding the audience permission, clocked in if asked, and holding the market's language skill at the market's minimum level if asked; when nobody matches, the holders of the fallback permission. The market is the record's, else its contact's country. A market outside the catalog matches nobody on language (so the fallback applies); a market without a language skill matches everyone. A message is written even when nobody receives it, so the stats show it. The link comes from the connection setting `record_url_<record type>`, a template with `{app_host}`, `{account}` and `{id}`, so no vendor's address pattern lives in the database. Answers how many messages were written |
| `cma.send_message(title, body, urgency, target)` | a manager's message (`messages.send`). The target names exactly one group: `{"everyone": true}`, `{"teams": [keys]}`, `{"language": {"skill", "minLevel"}}` or `{"users": [ids]}`, optionally with `"onlyClockedIn": true`. Resolved to active people now; a target that reaches nobody is refused |
| `cma.my_messages(since?, limit?)`, `my_unread_count()`, `mark_messages_read(ids)`, `acknowledge_message(id)` | a signed-in person's own deliveries only, newest first, expired ones left out. The first return sets `delivered_at`; acknowledging also reads |
| `cma.message_stats(from, to)` | per message in a business-date range of at most 92 days: recipients, delivered, read, acknowledged and the median seconds to read (`messages.send` or `performance.team`) |

"Clocked in" (`cma.is_clocked_in`) means an open workday that has started, pauses included; a day forgotten past its end is closed by the scheduler (0005a). Reporting views in `cma_read`: `message` (title and body hold references only, so both are included), `message_delivery` and `message_rule`. The application never deletes from these tables, never updates a message, and updates a delivery only in its three times (column privileges).

The verify (`43`) proves structure and privileges. On throwaway tenants it then proves:

- rules and their refusals;
- a rule reaching only the agents clocked in with the market's language at the minimum level;
- the market taken from the contact;
- the fallback, and a rule without one;
- a market without a language skill;
- `only_clocked_in` false;
- the age limit, from the setting and from the rule;
- idempotency;
- a disabled rule;
- pipelines that are not counted and pipelines not yet seen;
- deleted and unknown records;
- resolution at send time;
- the link and its refusals;
- the content;
- `delivered_at` set once and only for the caller, `since`, `limit` and expiry;
- read and acknowledge on own rows only, with times that never move back;
- every target of `send_message`, with its refusals and its permission;
- the stats;
- the Ingest user unable to configure, send or read, and a configuring person unable to raise alerts;
- tenant isolation and no deletes.

**Withdrawal (addition 0008z, 20 October 2026).** A message, manual or alert, can be withdrawn for everyone by a person holding `messages.withdraw` (the default ladder's admin: `94` grants it to the admin role of every existing tenant, and `cma.seed_default_roles` to a new tenant's). `cma.withdraw_message(id)` sets `withdrawn_at` and `withdrawn_by` once; a second call changes nothing and answers the first time; an unknown or another tenant's message is `CMA02`. The trigger `cma.check_message_change()` refuses any other change to a message (`CMA04`) and a second withdrawal (`CMA03`), and the application may update those two columns only. The row is never deleted: the audit keeps who and when, `cma.message_stats` marks it withdrawn, and `cma_read.message` carries both columns. A withdrawn message leaves every recipient's inbox and unread count (`my_messages`, `my_unread_count`) and can no longer be read or acknowledged. A delivery not yet made is never made: the poll is the delivery, so a message withdrawn before a recipient's next poll never reaches them. No realtime service exists yet (Features 7: the poll every 10 seconds); when it comes, its relay must check `withdrawn_at` before it pushes. `43` is amended for it (20 October 2026): its check A3 asserts this rule once `0008z` is recorded, as `95` proves it by behaviour (C6, C7), and A5 the two columns on `cma_read.message`. The web: Delete on Messages (the inbox and the sent list, where a withdrawn message stays marked Deleted) with the confirmation "Delete this message for everyone? Recipients will no longer see it.", Cancel focused; `POST /api/v1/messages/{id}/withdraw`.

### Data model: assignment alerts and automation messages (addition 0008a)

Written on 11 October 2026 for the go-live with Arno (`44_assignment_alerts.sql`, `45_verify_assignment_alerts.sql`), run and verified locally on PostgreSQL 18.6 (`44` twice, `45` passing and failing under provoke, `43` unchanged afterwards; outputs in `docs/night-2026-10-11/local-records/0008a/`). It needs 0008. Universal: the owner vocabulary is `app_user_external_id` with the system `<adapter>_owner`, the links come from the connection's templates, nothing names a vendor.

- **Assignment rules.** `message_rule.trigger` gains `record_assigned`: a record of the rule's type and pipelines whose owner maps to an active person raises one message for that person, `New <type> assigned to you` with the market, the pipeline label and the time, the record link, and the owner's source id as `target.assignee`; once per record and owner, so a reassignment alerts the new owner and a retry writes nothing. `cma.upsert_assignment_rule(name, record type, pipeline ids, urgency, max age?)` configures one (`tenant.configure`); the audience fields of 0008 are set to neutral values and never read for this trigger. The ingest service calls `cma.ingest_assignment_alerts(connection, record type, source ids)` after every read-back of records, created or changed (`ingest.write`; the age limit is the record's created or updated time against the rule's `max_age_minutes`, else `alerts.max_age_minutes`).
- **Uniqueness.** The one-alert-per-record index of 0008 now covers created alerts only (`where rule_id is not null and not (target ? 'assignee')`); `message_rule_ref_assignee_idx` covers assignment alerts per record and assignee; `cma.ingest_record_alerts()` is redefined with the matching conflict target, its body unchanged.
- **Messages from automations.** `cma.ingest_send_message(connection, title, body, urgency, target, ref system?, ref type?, ref id?)` (`ingest.write`) sends an announcement from the tenant's Ingest user to a target that names exactly one of `everyone`, `teams`, `language`, `users`, `owners` (`{ "system": "<crm>", "ids": [...] }`, the people behind CRM owner ids through `app_user_external_id` with the system `<crm>_owner`) or `emails` (work addresses, case-insensitive), optionally `onlyClockedIn`; the optional reference gives the link through the connection's `record_url_<type>` template. Resolved to active people now; nobody reached is CMA04, an unknown team, skill or person CMA02. The ingest service exposes it as `POST /automation/<connection key>` with `Authorization: Bearer <the connection's signing secret>` and a body `{ "messages": [ { title, body?, urgency?, target, ref? } ] }` (1 to 50): 404 for an unknown key or another adapter's connection, 401 for a wrong bearer, 400 with a code for a bad body, else 200 with `sent` (index, id, recipients) and `refused` (index, `invalid` or `not_found`), each message in its own transaction. A connection of adapter `automation` is created with `cma.upsert_connection('automation', name, <the CRM account id for the links>, <signing secret name>, null)` and the `record_url_*` settings.

### Data model: workday window and forgotten-day close (addition 0008b)

Written on 12 October 2026 (Martin's decisions of that day; `46_workday_window.sql`, `47_verify_workday_window.sql`), run and verified locally on PostgreSQL 18.4: `46` twice, `47` passing normally and failing under provoke (one FAIL per block), nine mutations of `46` caught, and `27`, `43` and `45` unchanged afterwards. Run in dev and prod on 12 October 2026 the same way (`46`, `47` passing and failing under provoke, then `02`, `27`, `43`, `45` again; records above); before prod, the one existing day ending after 22:00 was a team member's test day, now counted to 22:00. It needs 0008a. Universal: the window, the close time and who gets the digest are tenant settings; Pulse4all's values are seed data in `02_seed_pulse4all.sql` (07:00 to 22:00, 17:00, a grace of 60 minutes, for both tenants, set only where a tenant has no value yet). All times are local times in the day's own zone (the person's zone, kept on the day; Europe/Amsterdam and Europe/Madrid for Pulse4all, which keep the same clock).

| Setting | Type, default | Does |
|---|---|---|
| `workday.window_start` | time, `00:00` | the earliest clock-in of a working day: `cma.open_workday()` refuses a new day before it with `CMA04` and the message "the workday starts at HH:MI" |
| `workday.window_end` | time, `24:00` | the end of the working day: every stretch's counted time stops here (a stretch that begins after it counts nothing), an open day past it is capped and flagged, and the forgotten-day grace counts from it. Status changes and clock-outs after it are accepted: leaving is never blocked |
| `workday.auto_close_at` | time, `24:00` | where the scheduler ends a forgotten day when the person has no published shift that day |
| `workday.auto_close_notify_permission` | text, `workday.team` | who receives the digest of closed days (a permission key from the catalog) |
| `workday.auto_close_grace_minutes` | integer, 120 (since 0005a) | now counted from the window end |

The catalog gains the value type `time` (`HH:MI`, `00:00` to `24:00`); the settings trigger refuses a window that does not start before it ends and a notification permission outside the catalog. The universal defaults keep the behaviour from before 0008b for a tenant that sets nothing: a day from midnight to midnight, closed at its business day's end.

| Object | Does |
|---|---|
| `cma.business_day_end(date, zone)`, `cma.business_day_start(date, zone)` | the day's bounds from the current tenant's window (`24:00` is the next midnight, as before); every function that bounds a day calls these. Executable by the application only; `cma.business_day_time(date, zone, time)` is the plain arithmetic |
| `cma.time_interval_all`, `cma.workday_summary_all` | as in 0002 and 0005a with the window end of each row's own tenant, read in the owner's rights, so the readers' faces follow without access to the settings. One change in the counting: every stretch stops at the window end, not only an open one. Same columns, so every face and function above them is unchanged |
| `cma.open_workday()` | as in 0003d, plus the window start where a day is created |
| `cma.correct_workday()`, `cma.correct_time_event()` | times only within the corrected day's window (`CMA04` otherwise) |
| `cma.close_forgotten_workdays(grace?)` | a day still open after the window end plus the grace is ended at the person's published planned shift end for that date (the latest publication's entry, when it is a shift), else at `workday.auto_close_at`; never later than the window end and never earlier than the day's last effective event. Source `system`, the scheduler as acting user, as before; the result gains `end_rule` (`shift`, `default`, `last_event`). In the same transaction: one announcement per closed day to that person ("Workday closed automatically": "Your workday of Mon 12 Oct was closed automatically at 17:00 because you did not log out. Your supervisor will review it."), and per run one announcement to every active person holding the notification permission ("Workdays closed automatically": "4 workday(s) of Mon 12 Oct were closed automatically. Review them on Team hours."), without names or a reference, sent by the scheduler. Idempotent: a second run closes and sends nothing. The day stays `needs_correction` (0005a), so Team hours and Welcome's to-do line show it as before |

The web app reads the day's end with the own day (`dayEndsAt` on `GET /api/v1/me/day` and on the team now's `day`): the running clock on Welcome and My day, and the figure on Log out, stop counting there. A refused clock-in shows "The workday starts at 07:00" under the Clock in button, with the time the database gave, and the button stays. The mock follows the same rule with 07:00 to 22:00 and 17:00.

The verify (`47`) proves structure and privileges (the value type, the four settings with their defaults, who may execute the functions, the time views' columns and who reads them). On throwaway tenants, rolled back, with every time on a date two days back so the verdict does not depend on the hour, it proves:

- a tenant without settings counts as before;
- malformed and inconsistent settings are refused, and an agent cannot set them;
- a clock-in at 06:59 is refused with "the workday starts at 07:00", and one at 07:00 is accepted;
- a status change at 22:30 and a clock-out at 22:40 are accepted, with the counted time stopped at 22:00 for the application and for a reader;
- corrections outside the window are refused in both correction paths;
- four forgotten days close at the right end: a published shift ending 16:30 at 16:30 (`shift`), no shift at 17:00 (`default`), a last status change at 19:12 at 19:12 (`last_event`), a shift ending 23:00 at 22:00;
- each person gets one notice, every holder of `workday.team` gets one digest with "4 workday(s)", and nobody else gets either;
- the closed days stay flagged;
- a second run closes and sends nothing;
- the other tenant is untouched.

The verdict lists, per tenant, the window, the close settings and the open days past the window and its grace.

### Data model: legacy time import (addition 0008d)

Written on 12 October 2026 (Martin's decisions of that day; `50_legacy_time_import.sql`, `51_verify_legacy_time_import.sql`), run and verified locally on PostgreSQL 16 (with a local `uuidv7()` stand-in): `50` twice, `51` passing normally and failing under provoke (one FAIL per block), eight mutations of `50` caught, and `07`, `10`, `14`, `16`, `27`, `47` and `49` unchanged afterwards, also after `02`; an end-to-end run of the tool, the COPY file and the person map statement on a local tenant. It needs 0008c. Applied in dev and prod on 12 October 2026 after 0008c (Environments). Universal: nothing in the migration names a system, a tenant, a status key or a time; the source system, the work status, the gap status and the period are the batch's values, the window and the close time the tenant's settings. Pulse4all's import status is seed data in `02`; the run is `docs/import/README.md`.

**Status: loaded in prod 12 October 2026, batch `steam-2026`** (2026-10-12T13:02:18Z, `records/0008d-import-prod-2026-10-12`): 2353 sessions in, 462 merged, 1 open session dropped, none outside the window or unmapped, no account skipped; 1506 days written (23 closed by rule, 85 clipped, 1 dropped, none skipped as existing), 3778 events; 9,504.7 working hours over 13 people, 108 days flagged for a correction review (Open decisions). Before staging, 11 duplicated session ids were reduced to the row with the latest logout and the five management accounts were left out of the map (Decision log, 12 October 2026). Team hours and Correct a day show the days and the batch key as designed.

Why: the hours before the CMA lived in Steam Connect. Pulse4all's export (2 January to 9 October 2026) holds login and logout sessions only, in local time without an offset: no statuses, no breaks. Loading them as their own event source lets Team hours, the exports and the reports start on 2 January 2026 instead of on the CMA's first day, without a second hours store.

| Object | Does |
|---|---|
| `cma.time_event.source` `import`, `import_batch_id` | an imported event names its batch, and only an imported event does (a check); otherwise a fact like any other: append-only, effective until a correction supersedes or voids it |
| `cma.import_batch` | one file: key (unique per tenant), source system, file name, period, the zone of its local times, `staged`, `loaded` or `voided`, the work status and the gap status it writes; at load the snapshots of the window start and end and the close time, who loaded it, when and the counts; who voided it, when and why |
| `cma.import_session` | the file's sessions: account id and name in the earlier system, session id (unique per batch), login and logout in local time (no logout: never logged out), role. Written only by COPY into `cma.import_session_staging` (the staging file's columns, the batch by its key) by a person holding `tenant.configure`, into a staged batch; never changed |
| `cma.import_person_map` | which person of the tenant an account is (inactive people too, system users never); written by the same person into a staged batch; an account without a row is skipped and counted |
| `cma.import_day` | one row per day a load wrote: the workday, its end event, the sessions and merges behind it, the seconds, and whether it was closed by the open-session rule or clipped to the window |
| `cma.stage_import_batch(key, source_system, file_name, from, to, zone, work_status, gap_status)` | a staged batch; the statuses must exist and the period must end before today in the batch's zone; called again with the same values it returns the batch |
| `cma.load_import_batch(key)` | one transaction, rules below; returns the batch with its counts |
| `cma.void_import_batch(key, reason)` | withdraws the batch, below |
| `cma.workday_summary_all` | as in 0008b, same columns, two changes: `needs_correction` also covers an imported day closed by the open-session rule or clipped, while the import's end is effective (a correction that replaces the end clears it, as for a system end); a day without an effective start, which only a withdrawn import leaves, is no day |
| `cma.team_day()` | gains `import_batch_key`; the day editor's history shows "Imported from an earlier system, batch <key>" |
| `cma_read.import_batch`, `cma_read.time_event` | the batch without names (no file name, no free-text reason); the events gain `import_batch_id`. The sessions and the map have no reader view |

All four tables are tenant tables (`setup_tenant_table`: row-level security, the application's policy, audit). The application never deletes a batch, never changes a session, a map row or an imported day, and writes them only through the functions and the COPY target; the functions run as the caller (`cma_app`) and check `tenant.configure` inside, so an agent and a manager are refused and an admin is allowed.

**The load**, per mapped account and local login date, in the batch's zone with its snapshots (`cma.business_day_time`):

- a session without a logout ends at the close time (`workday.auto_close_at`); one that starts at or after it without a logout is dropped (`sessions_open_dropped`); the day is flagged closed by rule, as a system end is;
- every session is clipped to the window (`workday.window_start` to `window_end`); a session with nothing left inside it counts as `sessions_outside_window`; the day is flagged clipped;
- overlapping and touching sessions are merged (`sessions_merged`);
- one day from the first login to the last logout: the start in the work status, at every logout a status change to the gap status and at the next login back to the work status, the end at the last logout; source `import`, `occurred_at` the local time in the batch's zone, `recorded_at` now; then `refresh_workday`. So the working seconds of a day are exactly the sessions after the rules, and the gap status holds the gaps;
- a date that already has a day with effective events is skipped (`days_skipped_existing`: the CMA's own days win); the day of a withdrawn import is used again; a day under one minute is dropped (`days_dropped`);
- the work status is seeded inactive and never offered: no screen and no write path lets anyone choose an inactive status, and the load refuses an inactive work status only when it holds effective time on a workday that no import batch wrote (a day in `cma.import_day` of a batch that is not voided; since 0008zh, so a later batch reuses the tenant's import status). The corrections made to an imported day count as imported time, being events on the same workday; live clocked time and a day a supervisor added still refuse with `CMA04`. After a void the withdrawn events no longer count, so a reload works too. The load still retires the status, a no-op for one that is inactive already; the counts: `sessions_in`, `sessions_unmapped`, `accounts_skipped`, `sessions_open_dropped`, `sessions_outside_window`, `sessions_merged`, `days_written`, `events_written`, `days_closed_by_rule`, `days_clipped`, `days_dropped`, `days_skipped_existing`.

Refusals: a batch not staged (`CMA03`); an unknown status (`CMA02`); a work status that is not working, is the default, or is inactive with time on a workday no import batch wrote; a gap status that is working or paid; a map row outside the tenant; a session in the spring clock change gap of the batch's zone; a session that starts outside the period; a batch without sessions of a mapped account (all `CMA04`). A refused load writes nothing.

**The void** adds one void correction per effective event of every day the batch wrote, corrections made on those days since included, by the caller as approver with the reason "Import <key> withdrawn: <reason>". No fact is deleted and the day history keeps every row; the days then have no effective event, so the summary, Team hours, the exports and the Dashboard no longer count them, and a new batch may load the same person-days. Chosen over a status flag that hides a batch's events, because a void is the time model's own way to say an event did not count, with who and why, and it needs no change to the effective-event rule every read uses. A staged batch is simply marked voided. A reloaded day shows "Corrected afterwards", because its first import was withdrawn by a correction.

Imported days are kept in the batch's zone (Europe/Amsterdam for Pulse4all, the same clock as Newco's Europe/Madrid). The autumn change is outside Pulse4all's period; an ambiguous local time would take PostgreSQL's reading (the later, standard-time instant). The verify (`51`) proves structure and privileges, then on throwaway tenants with the dev window: agent and manager refused and the admin allowed; one batch with two overlapping sessions, an open session before and one after the close time, a session across the window end and one wholly after it, a login before the window start, three sessions with two gaps, a sub-minute day, an account without a map row, a date with a CMA day and an inactive person; the exact counts, seconds and gap seconds per day, the flags, the events and their batch, Team hours, the status-changes export (entered by import), the day history's batch key, a reader's view without the sessions; the work status retired, a second load and rows into a loaded batch refused; another tenant sees and loads nothing; the void and a reload on the same workdays; seventeen refusals, among them an inactive work status with live time behind it; and an inactive work status nothing was ever booked on, as the import status is seeded, that loads.

Known limit (0008zh): time corrected into the status on an imported day cannot be told from imported time, so a retired status whose only time was put there by corrections on imported days can be reused.

### Data model: sources configuration (addition 0008e)

| `cma.legacy_call_outcomes_upsert(batch, rows)` (`ingest.write`) | at most 500 rows `{sourceRow, occurredOn, meaning, sourceLabel, contactId, matchMethod}` of a live batch, each dated before the cutover date, the method one of `email_phone`, `email`, `phone`, `customer_id`, `none` or `conflict` (`forgotten` only the privacy deletion sets). **Definitions:**
- legacy call outcome and its match methods: docs/definitions.md, Legacy call outcome. Its day is the date the file writes, taken as the tenant's local date; no time of day is kept.
- volume, outcome and coverage: every stored row of a batch that is not withdrawn counts for volume and outcome; only a row with a contact counts for coverage. A row that matched no contact is stored as `none`, a conflict as `conflict`, both without a contact, unless the import runs with `--unmatched skip` (below).

**The import job** (`ingest-import-legacy-calls`, manual, no schedule; `ingest/src/jobs/import-legacy-calls.mjs`, `docs/ingest/README.md`, Jobs; the runbook is `docs/import/legacy-calls.md`). It reads one file from a private EU bucket into memory (`ingest/src/core/storage.mjs`, the job's service account holds `storage.objectViewer` on that bucket only, `docs/ingest/deploy.sh`), keeps its SHA-256 and drops the bytes once parsed. Every value is an argument: the connection, the file, the source system, the cutover date, the date format, the columns by role (`tag`, `date`, `source_marker`, and optionally `email`, `phone`, `customer_id`), the tag texts' meanings, and `--min-customer-id-digits` (default 10; a shorter or non-numeric customer id is not looked up). A row with the marker column filled is the former system's, an empty one the current system's; the current system's rows are only reconciled through `cma.legacy_call_reconcile` (found or not found, nothing stored). A former-system row is matched to exactly one contact per key through the HubSpot adapter (`ingest/src/adapters/hubspot/match.mjs`): the email (the primary, then the additional emails), the phone (E.164 only, searched by its national number on HubSpot's searchable phone properties and confirmed by the full number; a search with more than 5 candidates cannot be confirmed and reads as several), and, when neither found exactly one contact, the customer id, first among the store customers the CMA linked (0008h), then in the connection's contact ref fields. The lookups are counted in every progress line and in the finished line, so a lookup that never finds anything shows within the first hundred rows. The outcomes are written every 100 rows, each part its own transaction, at HubSpot's search pace and above the connection's `api_daily_floor_pct`; a run that reaches the floor finishes as succeeded with `daily_floor` and the same command later reuses the batch and skips the rows that hold a contact or were forgotten. The option `--unmatched store|skip` (default `store`) decides what happens to a row that matched no single contact: `skip` does not write a row whose method is `none` or `conflict`, so only rows matched to exactly one contact are stored (Pulse4all's choice, Decision log, 26 October 2026); the skipped rows are counted per method (`skipped_none`, `skipped_conflict`) and listed by row number in the log only, never in the batch's `counts`, so `cma.legacy_call_counts_ok()` is unchanged and a batch's `legacy` minus `stored` gives the skipped number. A rerun with `skip` inserts a row that now matches and leaves a row a `store` run wrote earlier as it is. The job takes the job lock: a second execution started while the first still runs logs "skipped" and exits 0.

A dry run (`--dry-run`) reads and checks the file, reconciles the current system's rows and checks that the portal holds the five HubSpot properties the lookups rely on (`hs_additional_emails`, `hs_searchable_calculated_phone_number`, `hs_searchable_calculated_mobile_number`, `phone`, `mobilephone`); it searches no contact and writes nothing (no batch, no outcome, no `sync_run` row). A real run checks the properties before any lookup too (`property_missing` otherwise).

**Choices made in the build.** One live batch per file, not one per tenant (the partial unique index above). Besides the functions the brief named, `cma.legacy_call_reconcile`, `cma.assert_legacy_crm_connection` and `cma.legacy_call_counts_ok`. A rerun never changes a stored row's date, meaning or label (`CMA03`) and never refills a forgotten row. `matched_at` is set exactly with a contact. The outcome's CRM connection is forced to the batch's. The run's job name is `legacy_call_import` with the existing count keys. Every personal value (email, phone, names, customer id) lives in the job's memory only, in this run: the log lines and the finished line hold counts and row numbers.

Everything is `SECURITY INVOKER` and executable by the application only, with its permission checked inside; the application never deletes a batch or an outcome. The verify (`109`, dev only) proves the structure and privileges (6 checks: the addition row after 0008zf; the two tables' columns; row-level security with the tenant policy, the audit trigger and no delete, nothing for the readers; the keys and checks, among them one live batch per file, the contact exactly with its methods and `matched_at` exactly with a contact; every function the application's only and in the caller's rights, `cma.ingest_contact_forget()` carrying 0008n's tasks and 0008zg's outcomes; the reporting views' exact columns, withdrawn batches left out, and the job name) and the behaviour on two throwaway tenants, rolled back (12 checks: a batch started, reused for the same file and refused for another cutover, another kind of connection, an inactive one, a bad SHA-256 and an agent; the rows of every match method; an idempotent rerun; a contact filled only where none is set, a set one kept, the method changed between `none` and `conflict`, a changed fact refused; the refusals; the table's own checks; the finish with the per-method counts; the reconciliation read; the privacy deletion; the withdrawal, its audit, the reader view and the same file again as a new batch; tenant isolation; the job's sync run). The ingest's own verifiers are `ingest/verify/legacy-calls.mjs` (34 checks, pure, with the synthetic fixture `ingest/verify/fixtures/legacy-calls/legacy-calls.csv`) and `ingest/verify/deploy-script.mjs` (26 checks, amended for the eighth job) (`docs/ingest/README.md`, Verifiers); `npm test` in `ingest/` runs eighteen pure verifiers.

Data prerequisites (KPIs 11): the courtesy tag meanings of the Subscriptions Aircall connection set on Configuration → Sources, Tags (docs/definitions.md, Tag, Pulse4all Subscriptions mapping); Steam's courtesy export; the HubSpot searchable phone properties, whose fill the dev rehearsal confirms before the real file (`docs/import/legacy-calls.md`, 3a); the tenant's hash pepper (it exists since Aircall).
