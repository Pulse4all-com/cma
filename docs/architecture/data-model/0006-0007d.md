# Data model: migrations 0006 to 0007d

Part of the CMA documentation (README.md, Documentation map). Moved verbatim from README.md on 20 October 2026.

### Data model: ingest and CRM records (migration 0006)

Written on 9 October 2026 as the database half of speed-to-lead slice S1a; run and verified locally on PostgreSQL 18.6 (`30_ingest_crm_records.sql` twice, `31_verify_ingest_crm_records.sql` passing and failing under provoke, three mutations caught, every earlier verify unchanged apart from `27`, adjusted with it); dev and prod follow through the release flow. Universal: the adapter is a data value, nothing reads a vendor payload; the ingest API maps a source's events and records to the canonical shapes below.

| Table | Scope | Holds |
|---|---|---|
| `integration_connection` | tenant | one adapter instance per tenant and source account: `adapter` (data value), `external_account_id` (the portal id), an opaque `key` for the webhook address (unique across tenants, not a secret), the **names** of the signing and token secrets in Secret Manager, status |
| `connection_field` | tenant | which source property feeds which canonical field: records (deal, ticket, …) take `market` and `language`, contacts take `country`, `language` and one `ref` per other system (for example the commerce system's customer id) |
| `connection_pipeline` | tenant | source pipelines per record type with label, `is_counted` (test pipelines out of reporting; a pipeline not yet seen counts), `is_routed` (S3) and the work type skill (S2) |
| `connection_stage` | tenant | stages per pipeline with label, order and the source's own closed flag, refreshed from the source; a stage the source dropped is archived |
| `ingest_event` | tenant | one row per received event, unique on the adapter's event key: source type, canonical kind (created, changed, deleted, merged, restored, associated), object type and id, property, `occurred_at`, `recorded_at`, the event as received (ids only), status (received, processed, ignored, failed, needs_review), attempts, `next_attempt_at`, an error code |
| `crm_record` | tenant | thin mirror of deals and tickets: `source_system`, record type, source id, pipeline, stage, `owner_ref` (the source's owner id), `contact_source_id`, market, language, `is_closed` (from the stage, null while the stage is unknown), `closed_at`, source created, updated and deleted times, `synced_at`, raw (the requested properties only) |
| `crm_contact`, `crm_contact_ref` | tenant | the contacts records point to: country and language, and their ids in other systems; a contact is taken in only while a record of the same connection points to it, so the contact base is never mirrored; a deleted contact keeps its id and loses its attributes and refs |

| Function | Does |
|---|---|
| `cma.ingest_connection(key)` | the ingest API's first call, before a tenant is known: tenant, connection, adapter, portal id, secret names and the tenant's Ingest user; nothing for an unknown key or an inactive connection, tenant or user. `SECURITY DEFINER` owned by `cma_owner`, pinned search path, like `find_tenants_for_identity` |
| `cma.ingest_record_events(connection, events)` | records a batch (at most 500) of canonical events; a known key is not written again; answers every key with its id, whether it was new and its status |
| `cma.ingest_claim_events(connection, ids?, limit?)` | claims due events with `FOR UPDATE SKIP LOCKED`, counts an attempt and moves `next_attempt_at` forward (1, 2, 4, … minutes, at most 60), so a dead worker's claim comes back |
| `cma.ingest_finish_events(connection, ids, outcome, error?)` | processed, ignored or failed; a failure at `ingest.max_attempts` (setting, default 10) parks the event as `needs_review`; a finished event never reopens |
| `cma.ingest_upsert_records(connection, records)`, `cma.ingest_upsert_contacts(connection, contacts)` | the mirror writes, guarded by the source's updated time so an older read never overwrites a newer one (stale); deletion marks a record deleted, `closed_at` is the source's close time or the first time the CMA saw the record closed |
| `cma.ingest_upsert_pipelines(connection, pipelines)` | refreshes pipelines and stages from the source, keeping counted, routed and work type; records take their stage's closed flag |
| `cma.ingest_records_without_contact(connection, max age?)` | records still without a contact, for the sweeper's second read |
| `cma.upsert_connection()`, `set_connection_status()`, `set_connection_field()`, `set_connection_pipeline()`, `connections_all()` | configuration for `tenant.configure` (the admin), `connections_all()` with events in the last 24 hours, waiting and parked; the configuration screen comes later, Studio until then |
| `cma.connection_config(connection)` | the mapping as JSON, for the Ingest user or a configuring person |
| `cma.crm_records_per_day(from, to)` | the Dashboard read for `performance.team`: records created per business date in the tenant's zone, record type, market and pipeline, with how many are closed now; counted pipelines only, deleted records left out, at most 92 days |
| `cma.ensure_ingest_user(tenant)` | one **Ingest** system user per tenant (`ingest@system.invalid`, login system and id `ingest`, no clock) holding the non-assignable system role `ingest` with the one permission `ingest.write`; run for every tenant and by `create_tenant` |

The application never deletes from these tables (the mapping rows and contact refs excepted); reporting views in `cma_read` leave out raw payloads, the connection key and the secret names. The verify (`31`) proves structure and privileges (RLS, policies, audit, no delete, the grants, the one definer function with its search path, the Ingest user per tenant, the views' columns, the setting) and, on two throwaway tenants, configuration and its refusals, the lookup by key, idempotent events, claim and backoff, parking after the maximum, pipelines and stages, records with stale, closed, deleted and unknown, a pipeline refresh closing a record, contacts with not held, stale, refs and deletion, records without a contact, the Dashboard read with counting and its bounds, tenant isolation, the Ingest user out of the application's reach and the missing acting user.

### Data model: intake core (migration 0007)

Written on 10 October 2026 as intake track I1 from `docs/night-2026-10-10/DESIGN.md` §3 and §4.1 (brief B1); run and verified locally on PostgreSQL 18.4 (`32_intake_core.sql` twice, `33_verify_intake_core.sql` passing and failing under provoke, twelve mutations caught, every earlier verify unchanged, outputs in `docs/night-2026-10-10/local-records/0007/`); run in dev and prod on 10 October 2026 (`records/0007-dev-2026-10-10`, `records/0007-prod-2026-10-10`). Universal: markets, hours, forms and outcomes are tenant configuration, vendors are data values, and nothing personal is stored (no names, emails, phone numbers, addresses or free text; a phone number exists only as a keyed hash made by the ingest service).

| Table | Scope | Holds |
|---|---|---|
| `market` | tenant | the countries a tenant serves: ISO 3166-1 code in upper case (`GB`, never `UK`), name, IANA zone, ISO 639-1 language, the language skill and minimum level for routing, ISO 4217 currency, status, order |
| `market_alias` | tenant | how sources write a market (`uk`, `united kingdom`, `nederland`), lower-cased, to its code; `cma.normalize_market()` reads it (alias, then a known code, else the value as written) |
| `business_hours`, `business_holiday` | tenant | office hours per market and weekday in local time, `*` as the default; a market with hours of its own uses only those; ranges of a day never overlap; holidays per market, `*` holidays apply everywhere |
| `crm_call` | tenant | call engagements held by the CRM: time, direction, status, outcome, duration, owner, the app that logged it, `counterpart_hash` (HMAC of the other party's number, never the number); stale guard on the source's updated time; a deleted call loses hash and raw |
| `connection_call_outcome` | tenant | the source's call outcomes with `is_connected` (configuration), refreshed from the source |
| `crm_association` | tenant | which call or record belongs to which contact, and which call to which record, in one stored direction; a removal keeps the row with `removed_at`, a re-add clears it, an older change than the stored one is ignored |
| `connection_form`, `form_submission` | tenant | forms with counted, lead source, market and `kept_fields` (field names whose values are not personal); submissions with ids, form, time, page host and path without query string, five UTM tags, the resolved contact id and its resolution, values only of kept fields (filtered again in SQL); insert-only apart from the resolution |
| `sync_cursor`, `sync_run` | tenant | where a poll or backfill stream stands; every backfill, reconcile, poll, subscription check or link run with range, counts and outcome, finished once |

Additive changes to 0006 objects, every 0006 call shape unchanged: `integration_connection.settings` (flat, non-secret, at most 4 kB, keys containing secret, token, password or key refused); `connection_field` with `currency`, `store`, `amount`, `source_channel`, `category` and a `slot` (above 1 for refs only); `crm_contact_ref.slot` (two commerce ids on one contact); `crm_contact.currency` and `store`; `crm_record.amount`, `currency`, `source_channel`, `category`; `connection_pipeline.is_lead`; the record and contact upserts take the new keys and normalise the market and country. Settings: `intake.start_date` (a new value type `date`), `speed_to_lead.pre_window_minutes`, `speed_to_lead.target_minutes`, `lead_to_order.max_days`, `forms.deal_window_hours`, `commerce.renewal_source_names`, `commerce.renewal_app_ids`, `alerts.max_age_minutes`.

| Function | Does |
|---|---|
| `cma.upsert_market()`, `set_market_status()`, `set_market_alias()`, `remove_market_alias()`, `set_business_hours(market, weekday, '09:00-12:30,13:00-17:00')`, `set_business_holiday()`, `remove_business_holiday()` | configuration for `tenant.configure`; `UK` is refused with "use GB", as are lower-case codes and unknown zones |
| `cma.business_seconds(market, from, to)`, `cma.next_business_noon(market, at)` | office seconds between two instants in the market's zone, holidays out, each day placed in the zone separately (so the 25-hour day of a DST change counts right); 12:00 local on the next working day |
| `cma.set_connection_settings()`, `set_connection_field(…, slot)`, `set_pipeline_lead()`, `set_form()`, `set_call_outcome()` | the connection's configuration (`tenant.configure`); `connection_config()` now also gives slots, `isLead` and the settings |
| `cma.set_user_external_id(user, system, id)`, `remove_user_external_id()` | a person's CRM owner or telephony user id for attribution (`users.manage_all`); the system must read `<system>_owner` or `<system>_user`, so a sign-in id or a system user is never touched |
| `cma.ingest_upsert_calls()`, `ingest_upsert_associations()`, `ingest_upsert_call_outcomes()`, `ingest_upsert_forms()`, `ingest_upsert_form_submissions()`, `ingest_cursor_get()`, `ingest_cursor_set()`, `ingest_sync_run_start()`, `ingest_sync_run_finish()` | the ingest write path (`ingest.write`), at most 500 items per call |
| `cma.ingest_contact_forget(connection, contact)` | privacy deletion: the contact's attributes and refs cleared, the hash cleared on its calls, kept values cleared on its submissions; ids and times stay for counts |

Reporting views in `cma_read`: `market`, `market_alias`, `business_hours`, `business_holiday`, `crm_call` (no raw, no hash), `connection_call_outcome`, `crm_association`, `connection_form`, `form_submission`, `sync_run`; `crm_contact`, `crm_contact_ref` and `connection_pipeline` gain their new columns; the record's new columns sit in `crm_record_detail` (joined on id), because `31` pins the column list of `cma_read.crm_record`. Sync cursors have no view. The application never deletes from the new tables except the mapping rows (aliases, office hours, holidays), and may update a submission only in its resolution and kept values and a run only in its outcome (column privileges). The verify (`33`) proves structure and privileges and, on throwaway tenants, markets and their refusals, alias normalisation, business seconds on a weekday, across a weekend, a holiday and the DST change of 25 October 2026, outside hours, reversed and for an unknown market, the next business noon from a Friday afternoon, the date setting, connection settings refusing secret-looking keys, the field mapping with slots and its refusals, records and contacts with the new fields and two ref slots, calls inserted, updated, stale and deleted, associations added, removed, re-added and an older change ignored, the outcome and form catalogs keeping their configuration, submissions idempotent with kept values filtered, cursors, a run finishing once, the privacy deletion, the Ingest user unable to configure and a configuring person unable to ingest, people's ids and their refusals, and tenant isolation for every new table.

### Data model: telephony (migration 0007a)

Written on 10 October 2026 as intake track I3 from `docs/night-2026-10-10/DESIGN.md` §4.2 (brief B2). It was run and verified locally on PostgreSQL 18.4: `34_telephony.sql` twice, `35_verify_telephony.sql` passing and failing under provoke, 18 of 19 mutations caught, every earlier verify unchanged. The outputs are in `docs/night-2026-10-10/local-records/0007a/`. Run in dev and prod on 10 October 2026 (`records/0007a-dev-2026-10-10`, `records/0007a-prod-2026-10-10`). Universal: the telephony system is a data value (`source_system`, the connection's adapter) and nothing personal is stored. The other party's number exists only as the keyed hash the ingest service makes (DESIGN §6.3), never shown and never returned by a function; it has three purposes, each inside one tenant: the link to the CRM call that logged the call (0007a), matching commerce orders to earlier calls (0008g) and matching missed inbound calls to later callbacks (0008i). Comments, recordings and voicemail links never arrive, and a line's digits are the company's own number.

| Table | Scope | Holds |
|---|---|---|
| `telephony_call` | tenant | the telephony system's calls: direction (inbound, outbound), status, missed reason, started, answered and ended, duration, `talk_seconds` (derived by the database: ended − answered, null while unanswered), the telephony user and line, archived, `counterpart_hash`; `source_version_at` (the newest event or read time) is the stale guard, so events that arrive out of order end in the right state; a deleted call keeps its id, times and tags and loses hash and raw; raw keeps flat, non-personal keys only (filtered again in SQL) |
| `telephony_tag`, `telephony_call_tag` | tenant | the tag catalog with `is_counted` (configuration); the tag history per call: a row per tagging, closed when the tag leaves the call's tag set, a new row when it comes back |
| `telephony_number` | tenant | the company's own lines: name and E.164 digits from the source, market and `is_counted` as configuration |
| `call_link` | tenant | a telephony call paired with the CRM call that logged it (`hash_time`: equal hash, same direction, at most 120 seconds apart) with the time difference; one current link per side; never rewritten, a wrong link is retired with the person's id and that pair is never linked again |

| Function | Does |
|---|---|
| `cma.ingest_upsert_telephony_calls(connection, calls)` | the call write (`ingest.write`, at most 500): inserted, updated, stale, deleted or unknown; each call may carry its whole current tag set, and tags are opened and closed by difference at its `source_version_at` (a call without a tag set leaves its tags, an empty set closes them); a tag not yet in the catalog joins it |
| `cma.ingest_upsert_telephony_catalog(connection, kind, items)` | refreshes the `tag` or `number` catalog, keeping `is_counted` and the market; entries missing from the source are archived |
| `cma.set_telephony_number(connection, line, market, counted)`, `cma.set_telephony_tag(connection, tag, counted)` | configuration for `tenant.configure` |
| `cma.link_calls(since)` | pairs telephony calls started since then with CRM calls of the same tenant, nearest first, each side once (partial unique indexes decide, so two sweeps at once cannot double a side); null hashes, deleted calls and retired pairs are left out; `ingest.write` (the sweep) or `tenant.configure` |
| `cma.unlink_call(link)` | retires a wrong link (`tenant.configure`); the next `link_calls` may pair either call with another candidate |
| `cma.ingest_contact_forget(connection, contact)` | as in 0007, and the hash is also cleared on telephony calls linked, now or formerly, to the contact's CRM calls; the answer gains `telephony_calls` when one was cleared |

Reporting views in `cma_read`: `telephony_call` (no raw, no hash), `telephony_call_tag`, `telephony_tag`, `telephony_number`, `call_link`. The application never deletes from these tables. Since addition 0008f a connection stores calls on its counted lines only, and a line switched off loses its calls (Data model: uncounted lines). A tagging changes only in its end and a link only in its retirement, each once (column privileges and a trigger). The verify (`35`) proves structure and privileges and, on throwaway tenants:

- a call written created, answered, ended in order and in reverse (ended first), ending in the same state with the stale guard
- unanswered and archived calls, the raw payload filtered, deletion and restore, refusals that write nothing
- tags closed and reopened by difference, stale reads and reads without tags, the catalogs keeping their configuration
- the link on hash, direction and 120 seconds, nearest first, each side once, null hashes and older calls left out, a second candidate left unlinked, unlink and what the next run links
- the privacy deletion reaching linked and formerly linked telephony calls and leaving the rest
- the Ingest user unable to configure and a configuring person unable to ingest, tenant isolation for every new table, and no deletes

### Data model: commerce (migration 0007b)

Written on 10 October 2026 as intake track I4 from `docs/night-2026-10-10/DESIGN.md` §4.3 (brief B3); run and verified locally on PostgreSQL 18.4 (`36_commerce.sql` twice, `37_verify_commerce.sql` passing and failing under provoke, nineteen mutations caught, every earlier verify unchanged, outputs in `docs/night-2026-10-10/local-records/0007b/`); run in dev and prod on 10 October 2026 (`records/0007b-dev-2026-10-10`, `records/0007b-prod-2026-10-10`). It needs 0007, not 0007a. Universal: a store is a connection with tenant configuration, the commerce vendor is a data value, and nothing personal is stored (no names, emails, phone numbers or addresses of customers; landing and referring pages as host and path only), with one exception since addition 0008g: customers and orders carry `phone_hash`, the keyed hash of the phone number, never the number (Data model: commerce phone hash; `36`'s header comment names it).

| Table | Scope | Holds |
|---|---|---|
| `commerce_store` | tenant | one store per connection: `handle` (lower case, digits and hyphens, unique in the tenant; the value the CRM's store field holds), name, market (from the catalog), currency, time zone |
| `commerce_customer` | tenant | a store's customers: state, locale, lifetime order count, amount spent with its currency, source times; stale guard on the source's updated time; a deletion keeps the id and times and clears state, locale, counts, amounts and raw, and only a read newer than the deletion brings the customer back |
| `commerce_order` | tenant | a store's orders: the shop's order number, customer id, created, processed, updated and cancelled times with the reason, `is_test` (test orders kept and flagged), currency and total, subtotal, tax, discount and refunded amounts, financial and fulfillment status, `source_name` and `app_ref` (the sales channel and app), landing host and path, UTM tags, referring host, order tags (at most 30), `prior_orders_count` with `prior_count_exact`, and `order_kind`; a deletion keeps ids, times, amounts, kind and lines and clears the pages, UTM, tags and raw |
| `commerce_order_line` | tenant | an order's lines: sku, product and variant ids, quantity, unit price, currency; replaced as a set when the order arrives with lines |

`order_kind` is computed in the upsert: `renewal` when the source name (without case or spaces) is in `commerce.renewal_source_names` or the app id in `commerce.renewal_app_ids` (both settings of 0007, empty until the subscription app's orders are named); else `first` when the customer had no earlier order, `repeat` when it had, `unknown` when the count is missing. A change to either setting reclassifies the tenant's orders in the same transaction (a trigger on `tenant_setting`); `cma.reclassify_orders()` reruns it on demand. One customer id in two stores gives two rows, one per connection; the join to the CRM is `crm_contact_ref` with the connection field's ref system and any slot, and a match in two stores is left to the data-quality views of 0007d. Since addition 0008h each customer also carries the CRM contact the ingest service matched it to (Data model: commerce contact link); the views of 0007d and lead to order still join through the refs (Open decisions).

| Function | Does |
|---|---|
| `cma.upsert_commerce_store(connection, handle, name, market, currency, zone)` | creates or updates the connection's store (`tenant.configure`); a handle another store holds is a conflict (`CMA03`), a market outside the catalog or an unknown connection `CMA02`, a malformed handle, currency or zone `CMA04` |
| `cma.reclassify_orders()` | recomputes `order_kind` for the tenant's orders (`tenant.configure`), answers how many changed |
| `cma.ingest_upsert_commerce_customers()`, `ingest_upsert_commerce_orders()` | the ingest write path (`ingest.write`), at most 500 items per call (and 500 lines per order); outcomes inserted, updated, stale, deleted, unknown, orders with their kind; hosts lower-cased, a path loses its query string, UTM keeps its five keys, tags trimmed, de-duplicated and kept to 30 of at most 60 characters |
| `cma.connection_config()` | as in 0007, plus the connection's store (handle, name, market, currency, zone), which the commerce adapter reads (the market is the phone hash's default region since 0008g; the CRM write-back it was first read for is unused since 0008h) |

Reporting views in `cma_read`: `commerce_store`, `commerce_customer`, `commerce_order`, `commerce_order_line`, none with the raw payload. The application never deletes stores, customers or orders; order lines are a child set replaced with their order (as contact refs are with their contact), and the audit trigger keeps every removed line. The verify (`37`) proves structure, keys and privileges and, on throwaway tenants, one store per connection and a unique handle (through the function and the keys) with the refusals and the store in `connection_config`; customers inserted, updated, stale, deleted and back only after a newer read, one customer id in two stores, the refusals; orders with lines replaced as a set, kept without the key and untouched by a stale read, `order_kind` first, repeat and unknown, renewal from each setting with reclassification on every change and on demand, test and cancelled orders kept and flagged, deletion, the normalisation of pages, UTM and tags, the refusals; the Ingest user unable to configure, a configuring person unable to ingest, and tenant isolation for every new table (another tenant's setting change included).

### Data model: outbox and CRM contact write-back (migration 0007c)

Written on 10 October 2026 as intake track I4 from `docs/night-2026-10-10/DESIGN.md` §4.3a (brief B13). Run and verified locally on PostgreSQL 18.4: `38_outbox.sql` twice, `39_verify_outbox.sql` passing normally and failing under provoke, a two-session claim test, 28 mutations caught and every earlier verify unchanged; the outputs are in `docs/night-2026-10-10/local-records/0007c/`. Run in dev and prod on 11 October 2026 (`records/0007c-dev-2026-10-11`, `records/0007c-prod-2026-10-11`). It needs 0007b (the store in `connection_config`), not 0007a or 0008. Universal: the fields, their target properties and modes are tenant configuration per CRM connection, and the payload holds ids, a store handle, counts, an amount and codes, never personal data (the ingest service drops the email it matched the contact with before it enqueues). The worker comes with the Shopify adapter (brief B10). **Since 13 October 2026 unused for commerce** (Decision log; addition 0008h): the HubSpot–Shopify app writes the Shopify contact fields, so the CMA writes nothing back, no runbook step configures a write-back field, nothing enqueues an action and the job `ingest-outbox` has no schedule. The tables, functions and worker stay as they are, generic, for the next action towards another system.

| Table | Scope | Holds |
|---|---|---|
| `writeback_field` | tenant | per CRM connection: the canonical field (`commerce_ref`, `commerce_store`, `commerce_orders`, `commerce_spent`, `country`, `currency`, `language`), its slot (above 1 only for `commerce_ref`: a contact holds the ids of two stores), the target contact property (written by one field only per connection), the mode (`always`, `if_empty`, or `slot` for `commerce_ref` only), enabled; disabled, never removed |
| `outbox_action` | tenant | one row per action towards another system (today `crm.contact.set_properties`): connection, target type and id, the payload (canonical field → value, at most 4 kB), a dedupe hash, the reason, the state, attempts, next attempt, claimed and sent times, the system's answer (`result`, at most 4 kB), a short error, who asked (`created_by`) and who resolved a parked action (`resolved_by`, `resolved_at`) |

States: `pending`, `in_flight`, `sent`, `failed`, `needs_review` (parked for a person), `superseded` (a newer action for the same target) and `dropped` (by a person). They only move forward, enforced by a trigger: pending and failed go to in flight or superseded; in flight to sent, failed, parked or superseded (or in flight again when a dead worker's claim expired); parked to pending (retry) or dropped. Sent, superseded and dropped are final, and the target and payload never change; the application may update only the state columns and never deletes.

| Function | Does |
|---|---|
| `cma.set_writeback_field(connection, field, property, mode, enabled, slot default 1)` | creates or updates one field (`tenant.configure`); an unknown field or mode, the slot mode or a slot above 1 for another field than `commerce_ref`, an empty property `CMA04`; a property another field writes `CMA03`; an unknown connection `CMA02` |
| `cma.enqueue_contact_writeback(connection, contact id, values, reason)` | the ingest side (`ingest.write`): refuses unknown fields and malformed values, keeps only enabled fields (the store and totals only with the customer id they describe), answers null when nothing is left; the same payload as the contact's latest action answers that action (the dedupe), else a new pending action supersedes the contact's older pending and failed ones, so an older value is never written after a newer one |
| `cma.outbox_claim(connection, limit default 50)` | due actions (pending, failed after the backoff, in flight with an expired claim) with `FOR UPDATE SKIP LOCKED`, never two of one contact at a time; counts an attempt and sets the next 1, 2, 4 … 60 minutes ahead (as `ingest_claim_events`), which is also how long the claim holds; a due action a newer one has overtaken is superseded instead, an expired claim at the maximum is parked |
| `cma.outbox_finish(ids, outcome, result, error)` | `sent` with the answer, or `failed` with a short error code; a failure at `outbox.max_attempts` (setting, default 8) parks the action; only actions in flight change |
| `cma.outbox_resolve(id, decision)` | `retry` (pending again, attempts start over) or `drop` for a parked action, recording the person (`tenant.configure`); a retry is refused when a newer action for the same target exists |
| `cma.outbox_status()` | per connection and state: counts, oldest and newest, the next attempt due (`tenant.configure` or `reports.view`) |
| `cma.connection_config()` | as in 0007b, plus the connection's write-back fields (field, slot, property, mode, enabled) for the worker, which writes no other property |

Reporting views in `cma_read`: `writeback_field` and `outbox_action` (with the payload, without the dedupe hash). The verify (`39`) proves structure, keys, the column grants, the state trigger and the claim's `SKIP LOCKED`, and, on throwaway tenants: fields set and updated in place, disabled not removed, the slot rules and the refusals, the fields in `connection_config`; enqueue with only enabled fields, unknown fields and bad values refused, null when nothing is left, the dedupe, supersede per contact, a sent action untouched, the same payload again after another one, an inactive connection refused; one claim per action, the backoff, a dead claim returning, no claim while the contact is in flight, an overtaken claim superseded, parking after failures and after an expired claim, a sent action never reopened (functions, trigger, grants); retry and drop recording the person, a newer action blocking a retry, `outbox_status` and who may read it; the Ingest user unable to configure or resolve, a configuring person unable to enqueue, and tenant isolation for both tables. Two workers in two sessions (claims held open) are in the local run: disjoint claims, no waiting, and two concurrent enqueues for one contact serialised so the second supersedes the first.

### Data model: lead metrics (migration 0007d)

Written on 10 October 2026 as intake track I5 from `docs/night-2026-10-10/DESIGN.md` §4.4 (brief B4); run and verified locally on PostgreSQL 18.4 (`40_lead_metrics.sql` twice, `41_verify_lead_metrics.sql` passing and failing under provoke, twenty-five mutations caught, every earlier verify unchanged, outputs in `docs/night-2026-10-10/local-records/0007d/`). It needs 0007a and 0007b (and 0007, through them). No new tables: functions and reporting views over the intake tables. Universal: pipelines, markets, hours, targets and windows are tenant configuration; owners are matched through `app_user_external_id` with the system `<the call's or record's source system>_owner`, so no vendor name is in the code.

**Speed to lead, as computed.** The population is the deals of counted lead pipelines (`is_counted` and `is_lead`; a pipeline not yet seen counts), not deleted, created on or after `intake.start_date` in the tenant's zone. A deal's contacts are its primary contact and the contacts currently associated with it. Its calls are the CRM calls of its connection, not deleted, currently associated with the deal or one of those contacts, whose effective start (the linked telephony call's start while the link is current, else the CRM call's time) is at or after the creation minus `speed_to_lead.pre_window_minutes`. The first outbound call is the measured one; the row also gives the first call of any direction, whether an inbound call came first, and the first connected call (outcome `is_connected`, or the linked telephony call answered). Market: the deal's own mapped market first, then its primary contact's country, each through the market aliases (read again, so an alias added later applies to older deals) and only when it names a catalog market; `unknown` otherwise, and then the business measures are empty (data quality shows the values). Measures: `elapsed_seconds`, `business_seconds` (office time in the market), `within_target` (at most `speed_to_lead.target_minutes`), `before_next_noon` (before 12:00 on the next working day), `waiting_business_seconds` for open deals not called; for a deal not yet called, `within_target` and `before_next_noon` stay empty while it can still make them and turn false when it no longer can. Status `called`, `not_called_open` or `not_called_closed`. The agent is the person behind the first outbound call's owner, else behind the deal's owner.

| Function or view | Does |
|---|---|
| `cma.speed_to_lead_rows(from, to)`, `cma.speed_to_lead_summary(from, to, group)` | one row per lead deal created in a business-date range of at most 92 days; the summary by `day`, `market`, `agent` or `pipeline`: deals, called, median and 80th percentile business minutes over called deals, % within target and % before the next noon over the deals whose outcome is known, open not called (`reports.view` or `performance.team`) |
| `cma.lead_to_order_rows(from, to)` | per lead deal: how many commerce ids its contacts hold (any ref slot, the ref system equal to the order's source system) and the first of their orders that is not a test, not cancelled and not deleted, created after the deal within `lead_to_order.max_days`, with its kind, store and days (same permission) |
| `cma.intake_per_day(from, to)` | per business date and market: form submissions of counted forms (the form's market), deals and tickets created and closed (counted pipelines), calls in and out on counted lines (the line's market), calls carrying a counted tag, new commerce customers, first and repeat orders and renewals (the store's market; test and cancelled orders out) (same permission) |
| `cma.data_quality()` | the total of each check for the Data page (`reports.view` or `tenant.configure`): lead deals without a contact; their primary contacts without country or language; markets or countries written by a source that are not in the catalog; CRM owners and telephony users without a person; CRM calls without a contact; telephony calls without a link after 24 hours (once the tenant has CRM calls); commerce customers whose id no contact holds, or several contacts hold; write-backs parked for review (from 0007c on; empty until the outbox exists); contacts whose first two ref slots of a system are taken; contacts whose country differs from a store their commerce id belongs to; a commerce id in two stores; pipelines no person has ever written (only the source's refresh, read from the audit log); counted forms without a market |
| `cma_read.speed_to_lead`, `cma_read.lead_to_order`, `cma_read.intake_per_day_v`, `cma_read.dq_<check>` (fifteen) | the same rows, without a date range, for every tenant the reader sees; the `dq_` views give tenant, connection, object type, object id and a code where the check is about one, never personal data |

How the rows are made once: each read is a function of an explicit tenant (`cma.*_of`) in the caller's rights. The application's functions check the permission and call it for the current tenant under row-level security. A reporting view cannot call a function that reads schema `cma` in the reader's rights, so each view reads one of four `SECURITY DEFINER` functions in `cma_read` (nine since addition 0008o added five for the follow-up views) (owned by `cma_owner`, search path pinned with `pg_temp` last, executable by `cma_readonly` only), which call the same function for each tenant `cma_read.reader_sees()` allows. `cma.business_seconds()` and `cma.next_business_noon()` of 0007 keep their signatures and now share the code of `business_seconds_of()` and `next_business_noon_of()`.

The verify (`41`) proves structure and privileges and, on throwaway tenants with a constructed week (NL and GB, office hours, a holiday), every speed-to-lead case of brief B4 (7 business minutes; Friday 16:55 to Monday 09:10 as 15 business minutes and before the next noon; not called open and closed; an inbound call first; a call on the deal only and on a second associated contact; the pre-window both ways; a linked telephony call moving the start; a removed association; non-lead and uncounted pipelines out; the market from the deal through a later alias, from the contact, unknown; the agent through the call's and the deal's owner; a holiday), the summary in each grouping, the 92-day bound, lead to order (first, repeat through ref slot 2, renewal; test, cancelled and late orders out; the window as a setting), intake per day per market, every data-quality check firing exactly once and clearing when fixed, the permissions (an agent and the Ingest user refused, the supervisor without data quality), tenant isolation for the application and for readers, and the readers' views equal to the application's rows.
