**Tenant = business line.** A tenant is one isolated environment with its own people, configuration and data, inside the CMA database. Pulse4all Subscriptions and Pulse4all Invest are the two tenants; every tenant-scoped table carries `tenant_id`. `cma.create_tenant(slug, name, timezone)` creates a tenant with the default role ladder.

**Tables**

| Table | Scope | Holds |
|---|---|---|
| `tenant` | global | one row per business line: slug, name, time zone, status |
| `permission` | global | what the application code can check (`roster.manage`, `leads.accept`, …); changed only by migrations |
| `schema_migration` | global | which migration scripts have run |
| `organisation` | tenant | employers of the people in a tenant: the company itself and partners such as the call center. `name` is the display name the Workspace shows (Pulse4all's own: `Pulse4all`, since 7 October 2026); a legal entity name for invoices or payroll files becomes a separate `legal_name` column when needed, never folded into `name` |
| `channel` | tenant | customer contact channels with an `is_synchronous` flag; phone and email today, sms, whatsapp, chat, the Customer App and more as rows later. Skills, routing rules, SLAs and metrics reference a channel, nothing assumes phone |
| `app_user` | tenant | people who use the CMA, any employer, any email domain; one row per person per tenant, never hard-deleted |
| `app_user_external_id` | tenant | the same person in other systems, keyed by system; for Pulse4all `google` (login), `hubspot_owner` (lead assignment), `aircall_user` (call matching). Another customer uses its own system keys |
| `app_role`, `role_permission` | tenant | the role ladder per tenant (agent, supervisor, manager, analytics), seeded identically for every tenant and adjustable per tenant |
| `user_role` | tenant | role grants, optionally scoped to a team or market; the same role can be granted per scope |
| `audit_log` | tenant | every insert, update and delete on every tenant-scoped table, with before and after image, timestamp and actor; the application inserts and may read, never updates or deletes |

**Tenant separation**

- Hard separation between customers is the database boundary (see Customers, databases and tenants). Everything below separates business lines within one customer.
- Row-level security on every tenant-scoped table. The application sets its context once per transaction with `set_config(..., true)`: `app.tenant_id`, `app.user_id` (the acting CMA user) and optionally `app.actor_label` (the acting process, for example `ingest-api:hubspot`). No tenant set means nothing is visible and every write is rejected.
- Composite foreign keys on `(tenant_id, id)`, so a role, team or employer from one tenant can never be attached to a row of another.
- `cma.setup_tenant_table(table)` applies RLS, grants and the audit trigger. One line per new table in every migration.
- This protects against a forgotten `WHERE`, not against a hostile application: the app is trusted for the tenant it authenticated.

**Conventions for every migration**

- System names (hubspot, aircall, zoho, activecampaign, …) appear only as data values, never in table, column, function or role names
- Every migration starts with the personal-login guard and `set role cma_owner`, is rerunnable, and ships with its verify script, because it runs in dev, then in prod, and unchanged in any later database
- Every script runs under a personal IAM login; `postgres` only for a declared emergency, so audit rows always name a person
- `timestamptz` everywhere; the business day is derived from the configured time zone (tenant now, site or market later)
- Facts such as time entries, attempts, lead assignments and notifications are append-only, with `occurred_at` (when it happened) and `recorded_at` (when we wrote it); a correction is a new row with reason and approver, and closed periods are locked
- Facts that affect pay, billing or reporting over time (employment, team membership, skills, rates, targets) carry `valid_from` and `valid_to` and are never overwritten
- Configurable catalogs carry semantic flags (paid, billable, productive, synchronous, outcome, sets do-not-call), never names only, so billing, adherence, SLAs and the queue never depend on a string match
- Synced data carries `source_system`, `source_id`, `synced_at` and the original payload in `raw`; ingest is idempotent on system and id
- Consequences carry their cause (`closed_by_task_id`, `dnc_set_by_task_id`, `supersedes_event_id`), so nothing self-repairs silently
- Every table that reporting needs gets its `cma_read` view in the same migration, with its columns listed explicitly
- `uuidv7()` primary keys; status columns instead of hard deletes

| Table | Scope | Holds |

**The write path.** The application never inserts into these tables. ### Data model: roster (migration 0005)

Written in the night build of 7 to 8 October 2026 (slice 3); run and verified locally in the night (`23_roster.sql`, `25_verify_roster.sql`, blocks A and B1 to B13), in dev and prod on 8 October 2026 through the runbook (`records/0005-dev-2026-10-08`, `records/0005-prod-2026-10-08`); the dev fixture `24_seed_dev_roster.sql` writes this week's published rosters and next week's draft through the functions as the test manager. Universal: absence types and coverage targets are tenant rows, the adherence tolerance a tenant setting.

**Tables**

| Table | Scope | Holds |
|---|---|---|
| `absence_type` | tenant | the absence types with `key`, `name`, `is_paid`, `sort_order`, `status`; seeded by `cma.seed_default_absence_types()` (which `create_tenant` calls): `off` (a planned day off), `leave`, `sick`, `public_holiday`, `other`. Nothing medical beyond the word; no reasons are stored |
| `roster_week` | tenant | one roster per week per team, or for the whole tenant when `team_id` is null; `week_start` a Monday; `status` draft until first published, then published; `version` counts the publications; `published_at` and `published_by` the latest |
| `roster_publication` | tenant | every publish with its instant and person, insert-only, so what agents saw at any time is reconstructable from the versioned entries |
| `roster_entry` | tenant | one cell, versioned: `kind` shift (`start_time` and `end_time` local in the person's zone, within the business day, so 00:00 to 24:00 and never across midnight, README decision of 7 October 2026) or absence (`absence_type_id`), `note` (at most 200 characters), `recorded_at` and `recorded_by`; a change ends the row (`valid_to`, `superseded_by`) and inserts a new one, a clear ends it. At most one current entry per person per business date across every roster of the tenant (a partial unique index), so two team rosters cannot both plan the same person on a day |
| `coverage_target` | tenant | how many people holding a work type a team wants on a weekday; the planner shows planned against target |

The versioning instants (`recorded_at`, `valid_to`, `published_at`) are `clock_timestamp()`, not `now()`, so a publish and an edit in one transaction still order (the verify's B6 caught the difference).

**Setting.** `roster.adherence_tolerance_minutes` (integer, default 5): how late a clock-in or how early a clock-out may be before the Live board flags it.

**Functions (the application only, every one checking its permission inside)**

| Function | Does |
|---|---|
| `cma.roster_week(week, team?)`, `roster_people()`, `roster_entries()`, `roster_coverage()`, `roster_weeks(team, from, to)`, `coverage_targets(team)` | the planner's reads (`roster.manage`): the week's header (state, version, publication, entry count, `changed_since_publish`), the people on the grid (whose time is kept and, for a team roster, who is a member during the week, with their work types), the current cells, people on shift per work type per day with the target, the weeks of a range as a calendar with state and counts |
| `cma.roster_set_entry(week, team?, person, date, kind, start, end, absence key, note)` | one cell: a new version, the old one ended; `kind` null clears. The past for that person (today in their zone is open), a date outside the week, a person not on the grid and bad times are `CMA04`; another roster's entry on that date `CMA03`; an unknown absence type `CMA02` |
| `cma.roster_publish(week, team?)` | publishes the week as it stands: version + 1, a publication row; a week never written is created and published empty |
| `cma.roster_copy_week(from, to, team?)` | copies the current cells of one week into another of the same scope: a source cell overwrites the target cell, an empty one leaves it alone, the past and people no longer on the grid are skipped |
| `cma.my_roster(from, to)` | the caller's own schedule (`roster.view`), one row per date, published entries only as of each week's latest publication, with `is_published` saying whether a published roster covers the person that day at all; at most 92 days |
| `cma.roster_today()` | today's published entry per person whose time is kept, in each person's zone, for the Live board (`monitoring.live`) |
| `cma.absence_types()`, `cma.upsert_absence_type()`, `cma.set_coverage_target()` | the catalogs: read by any active person, written with `tenant.configure` and `roster.manage` |
| `cma.roster_published_entry` | the entries as agents see them (as of each week's latest publication), an owner-only core with a tenant face and a reader face; `cma_read` views for every table |
