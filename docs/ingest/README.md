# The ingest service (`cma-ingest`)

The only write path into the CMA from outside Google Cloud (README Architecture, Ingest API; specification `docs/night-2026-10-10/DESIGN.md` §2, §5, §6). Code in `ingest/` (plain Node 22, ESM, `pg` and the Cloud SQL connector as `web/src/lib/db/client.ts` connects). This version has the HubSpot route (brief B7), the jobs (brief B8), the Aircall route with its scripts (brief B9, section Aircall below), and the Shopify route with its subscription script (brief B10, section Shopify below), which since B10.1 keeps each customer's CRM contact in the CMA and writes nothing back; the outbox worker of B10 stays, generic and unscheduled (section Outbox); the email poll of HubSpot's email engagements and inbox conversations, metadata only (brief B17b, section Email below); and the reviews poll of Trusted Shops, which has no route and keeps metadata only (brief B18, section Trusted Shops below); and the asset register poll of Airtable, which has no route either, reads the mapped fields only and loads them through the device import's load (addition 0008zj, section Airtable below); and the subscriptions poll of Juo, which has no route either and keeps ids, codes, counts and times of a store's subscriptions and their events only (addition 0008zl, section Juo below).

## What it does

| Route | Does |
|---|---|
| `GET /health` | `{"ok":true,"version":"<short sha>"}`; no database |
| `POST /hubspot/<connection key>` | a HubSpot webhook batch: key → connection (`cma.ingest_connection`), v3 signature, events recorded and committed, objects read back within 3 seconds, then `200 {"received":n,"new":m}` |
| `POST /aircall/<connection key>` | one Aircall webhook event: key → connection, the body's `token` against the connection's signing secret, the event recorded and committed, the call read back from Aircall within 3 seconds, then `200 {"received":1,"new":0 or 1}` (section Aircall) |
| `POST /shopify/<connection key>` | one Shopify webhook delivery: key → connection, `X-Shopify-Hmac-Sha256` over the raw body with the app's client secret, the event recorded and committed, the customer or order read back through GraphQL within the route's own 1.5-second budget, then `200 {"received":1,"new":0 or 1}` (section Shopify) |

Answers: unknown key, inactive connection, a connection of another adapter, an unknown route or a method other than POST → `404`, empty. An adapter that only polls has no route either: `/trustedshops/<connection key>` and `/airtable/<connection key>` answer `404` like an unknown adapter (sections Trusted Shops and Airtable). A bad, missing or stale signature (Aircall: a missing or wrong token, or a body that is not JSON; Shopify: a missing, malformed or wrong HMAC) → `401`, empty, nothing written. A body over 1 MB → `413`. A body that is not JSON → `400`. A database error before the commit, or a signing secret that cannot be read → `500` (HubSpot sends again).

Per request, in this order (DESIGN §2, the 0006 pattern):

1. **Authenticate** before anything but the key lookup touches the database: `X-HubSpot-Signature-v3` = base64(HMAC-SHA256(client secret, `POST` + URI + body + timestamp)), `X-HubSpot-Request-Timestamp` at most 5 minutes off, compared in constant time. The URI is the public address HubSpot called: the service's own URLs are in `INGEST_PUBLIC_URLS` (deploy.sh sets both Cloud Run address forms; in prod with `--front <host>` the public host `https://<host>` comes first, so HubSpot signs the public host).
2. **Record** every event as a canonical event (`hs:<eventId>`, kind, object type and id, ids and timestamps only; the property value and the acting user are dropped), in one transaction, in batches of at most 500. An event of another portal is recorded as `ignored` with `raw.ignored = portal_mismatch` and never read back; so are association changes the CMA does not keep (only deal → contact, ticket → contact, call → contact and call → deal) and objects it does not read.
3. **Read back** within the budget (`INGEST_READBACK_BUDGET_MS`, 3000): deals and tickets by CRM v3 batch read with HubSpot's structural properties (pipeline, stage, owner, created, closed, modified) plus the properties configured in `cma.connection_field`, their contacts through the v4 associations batch read, the primary contact (labelled primary, else the one already held, else the lowest id) read with its configured properties; calls with their properties, the other party's number hashed (below) and dropped, their contacts and deals; contacts only when the CMA holds them (0006: never the contact base). Deletions mark the object deleted without a read; `contact.privacyDeletion` calls `cma.ingest_contact_forget()`. Pipelines with stages and the call outcome list (`/calling/v1/dispositions`) are refreshed at most hourly per connection.
4. **Upsert** through the 0006 and 0007 functions (stale guard on the source's updated time) and **finish** the events. A 429 finishes them as `failed` with `rate_limited`, a timeout with `timeout`, an HTTP error with `http_<status>` (a redirect answer too: since 17 October 2026 no outbound call follows one, so a vendor token or the Shopify client secret never travels to another host), a body over 16 MB with `bad_response`: the sweep job reads them again with backoff and parks them after `ingest.max_attempts`.

Without a market property mapped for a record type, a deal or ticket takes its primary contact's mapped country as market (and language), normalised by the market aliases (VENDOR_SETUP §1.1). A later change of the contact's country reaches the record at the record's next read (its own event or the nightly reconcile of B8).

**Stage times and reasons (additions 0008za and 0008zb, brief N21).** A deal's read asks for HubSpot's calculated stage properties `hs_v2_date_entered_<stage id>` and `hs_v2_date_exited_<stage id>` of its pipeline's stages that read times (`connection_stage.read_times`, Configuration → Sources; the name built from the stage id, lower case, every other character an underscore) and writes them through `cma.ingest_record_stages`, which never clears a stored time. On the webhook route they ride in the same batch read when at least `INGEST_STAGE_READ_MIN_MS` (1500) of the 3-second budget is left and the stages need at most `INGEST_STAGE_READ_MAX_PROPERTIES` (400) properties; otherwise the record is written without them and a `stages:` event leaves the stage read to the next sweep, logged with its reason (`budget` or `properties`). The sweep, the nightly reconcile and the backfill read them always. A record type's reason comes from the property mapped as the field `reason`, and only from an enumeration: the sweep reads the property's definition (`GET /crm/v3/properties/{object}/{property}`) when its type is unchecked or an hour old, writes the type and an enumeration's options through `cma.ingest_upsert_reasons` (a person's data-quality flag stays), and until the type is enumeration the record read asks for no reason property at all; a text property is refused and Sources says so. A property HubSpot does not have is recorded as missing; any other failure (a 403 included) is logged as `reason property not read` with its code and tried again on the next sweep.

**The keyed hash.** `HMAC-SHA256(pepper, E.164)` in hex; numbers normalised with libphonenumber, national formats with the connection setting `phone_default_region` (for example `GB`) as default region; a number that is not a possible phone number gets no hash. The pepper is per tenant: secret `ingest-hash-pepper-<tenant slug>`. Without it, calls are not read back (`pepper_unavailable`) until it exists.

**Logs** are JSON lines: connection id, adapter, counts, durations and error codes. Never payloads, contact or customer ids, numbers, emails, secrets or header values. With `INGEST_LOG_HEADER_NAMES=1` (dev) each webhook logs its header **names**, so the first delivery shows whether HubSpot sends `x-hubspot-signature-v3`.

## Jobs

Cloud Run jobs on the same image (`node jobs/<name>.mjs`), as `cma-ingest@<project>` with the service's database settings but a pool of 2 (`CMA_DB_POOL_MAX=2`, the service 5; since 28 October 2026, the Gemini audit of that day, FIND-01: each job holds its advisory lock and one unit of work at a time, and no job runs two at once), one task and no retries (`--max-retries=0`), started by Cloud Scheduler (Europe/Amsterdam) as `cma-ingest-scheduler@<project>`, which holds `run.invoker` on the scheduled jobs only. Each serves every active connection of every tenant with an active Ingest user (`cma.find_tenants_for_identity('ingest', 'ingest')`, then the tenant's connections under row-level security, as the tenant's Ingest user), exits 0 when every connection was served and 1 when any failed (the others are still served). Logs: connection ids, counts, codes; never an email, a contact id or a token. One execution at a time (since 17 October 2026): each scheduled job takes a session advisory lock named for the job on one of its pooled connections for the run; an execution that finds it held, because the previous one is still running, logs `<job> skipped` with code `locked`, writes nothing (no `sync_run` row: the table knows `running`, `succeeded` and `failed` only) and exits 0, so Cloud Scheduler's next minute never piles a second run on a slow one (README, Database connection budget). The backfill and the outbox run by hand and take no lock; the legacy call import (addition 0008zg) runs by hand and takes the lock, so a second execution of it skips.

Reconcile, backfill and the second read do not write themselves (apart from the objects with a poll of their own: form submissions, email engagements and inbox threads go through their poll's path): what they find becomes a synthetic event (`sync:<type>:<id>:<modified time>`, kind `changed`) on the webhook's read-back and upserts. So an unchanged object is read once however often it is listed, a 429 in a backfill leaves its events to the sweep with backoff, and every object a job touched has its event row. A failed contact search in the forms poll writes nothing for that form and leaves its cursor, so the next run reads the same submissions again (they are idempotent on the conversion id). HubSpot's search returns at most 10,000 results per query; past that a new query starts at the last value seen. Deletions are not found by a search: they arrive by webhook.

## Aircall

The Aircall adapter (brief B9; DESIGN §2, §2.1, §4.2, §6), `ingest/src/adapters/aircall/`. The prod sequence is `docs/ingest/PROD_RUNBOOK.md` phase 8; this section is what each step relies on.

**Setup, once per Aircall company** (PROD_RUNBOOK 8.2 to 8.7): the API key into the token secret as one line of JSON `{"api_id":"…","api_token":"…"}` (Basic authentication on `https://api.aircall.io`); the connection with `cma.upsert_connection('aircall', <name>, <company name>, <signing secret>, <token secret>)` and its kind `telephony`; the signing secret created empty and both secrets granted to the service (`deploy.sh … --secret`); the webhook by `aircall-webhook.mjs`, which stores its token in the signing secret; the setting `webhook_id`; the lines' markets on Configuration → Sources; each agent's Aircall user id by `aircall-users.mjs`; the backfill.

**The account id is the company's name.** An Aircall event names no company, and `GET /v1/company` exposes no company id (in Pulse4all's account on 13 October 2026: `company.name` is `Pulse4all`, `company.id` is null). A request is pinned to its connection by the webhook's own token (one webhook per connection, its token in the connection's signing secret) and the opaque key in the path. The connection's `external_account_id` is the company's `name` exactly as `GET /v1/company` answers it, `Pulse4all` for Pulse4all's account: the value for PROD_RUNBOOK 8.3. `aircall-webhook.mjs --account <company name>` refuses to run when the API key answers for another company, so a key of another Aircall company is never wired to this connection, and the reconcile and the backfill make the same check first (`account_mismatch`, nothing listed). A renamed company in Aircall means updating the connection's account id (`upsert_connection` with the new name) before the next job.

**Per event** (one per request): the body's top-level `token` is compared in constant time (`crypto.timingSafeEqual` on equal-length buffers; another length is a failure) with the signing secret (Secret Manager, 5-minute cache); a failure is `401`, empty, nothing written. The event is recorded as `ac:<event>:<call id>:<timestamp>` (Aircall delivers at least once and not in order; the key absorbs the retries), ids and times only, never the token or the call object. Recorded and read back: `call.created` (kind `created`), `call.answered`, `call.ended`, `call.tagged`, `call.untagged`, `call.archived` (kind `changed`). Any other event, of a call or another resource, is recorded as `ignored` with `raw.ignored = event_not_handled` and never read back. Then, within the 3-second budget, the call is read with `GET /v1/calls/{id}` (a call Aircall does not know, 404, finishes `ignored`) into `cma.ingest_upsert_telephony_calls`: direction, status, missed reason, started, answered and ended (UNIX seconds to timestamps), duration, the user's id as `user_ref`, the line's id as `number_ref`, archived, the whole current tag set (tags opened and closed by difference), `raw` an allowlist (status, direction, missed_call_reason, duration, archived and the three times), and `source_version_at` the time of the read (the stale guard). The sweep reads a call once per batch however many of its events are due (in the webhook path each request carries one event, so each request reads once).

**The other party's number** (`raw_digits`) becomes the keyed hash (`HMAC-SHA256(pepper, E.164)`, `src/core/hash.mjs`) with the line's market (`cma.telephony_number.market`) as the default region for a national format, else the tenant's first active market (sort order, then code); it is never stored, logged or kept in an event. Without the tenant's pepper the call is not read (`pepper_unavailable`).

**Catalogs.** Lines (`GET /v1/numbers`: id, name, the company's own digits) and tags (`GET /v1/tags`: id, name) go into `cma.ingest_upsert_telephony_catalog`: from the sweep at most hourly per connection (cursor `catalogs`), and on the first event of a connection whose line catalog is empty. A line's market and counted flag and a tag's counted flag are configuration and stay (0007a); an entry Aircall no longer lists is archived. A catalog above 500 entries is not refreshed (logged as `catalog_too_large`). Pulse4all's account has 54 lines: each needs its market and counted flag on Configuration → Sources (no rule for lines yet). Since addition 0008f a connection stores calls on its counted lines only: a call on a line that does not count is read but not written (outcome `skipped_uncounted_line` in the `processed` log line; a reconcile or backfill run counts it as skipped), and switching a line off removes its stored calls. A new line arrives counted, so one Aircall company serving several tenants, each with its own connection and webhook, marks the other business lines' lines not counted (PROD_RUNBOOK 8.6).

**Pacing.** Aircall allows 120 requests per minute (developer.aircall.io: the API reference, Rate limiting, says per company; the best-practices page says per API key or OAuth token, and that exceeding it blocks access for 60 seconds). Pulse4all's account has three other keys in use by other integrations, so the adapter keeps to `aircall_max_per_minute` (a connection setting, default 60, at most 120; lower it on Configuration → Sources without a deploy), one pace per connection and process shared by the read-back, the catalogs, the reconcile and the backfill. The webhook path never waits past its budget for a slot (the event fails `paced` and the sweep reads it). On a 429 the rest of the batch is not tried: those events fail `rate_limited` and wait for their backoff, the log line `aircall rate limited` gives Aircall's `X-AircallApi-Limit`, `X-AircallApi-Remaining` and when calls resume, and the connection makes no call before `X-AircallApi-Reset` (at most 70 seconds; 60 without the header). Nothing retries in a loop. The pace is per process: the service and a job running at the same time can each use the limit, which stays under Aircall's 120 while the setting is 60 or less.

**Reconcile and backfill** list `GET /v1/calls?from&to` (UNIX seconds, the call's creation) in windows of one day, ascending, 50 per page; the list stops at 10,000 calls per query, so a window holding more is split in halves (`list_window_full` below a minute). The listing holds the full call, so a listed call is not read a second time: it becomes a synthetic event `sync:telephony_call:<id>:<fingerprint>` whose read-back takes the listed object (the fingerprint covers what the CMA keeps, never the number), so an unchanged call is written once however often it is listed. Reconcile: the calls created in the last 26 hours (a later change to an older call arrives by webhook only), then the webhook check: the webhook whose id is the setting `webhook_id` in `GET /v1/webhooks`. The run fails with `webhook_id_not_set` (no setting), `webhook_missing` (Aircall has no such webhook), `webhook_token_mismatch` (its token is not the signing secret: events would be refused), `webhook_inactive` (disabled and the re-activation failed) or `webhook_reactivated` (Aircall had disabled it after its deliveries kept failing: its documentation says after 50 retries in the API reference and after 10 failed attempts in the older webhook guide; the job set it active again with `PUT /v1/webhooks/{id}` and its own events, the token unchanged, and records that as the run's error so it is seen); `webhook_reactivated_token_changed` if Aircall ever answered the re-activation with another token (then run `aircall-webhook.mjs --delete` and create it again). A job never creates a webhook: a new one has a new token. Backfill: `--object telephony_call` from `intake.start_date` (or `--from`), resumable: the cursor `backfill:telephony_call` holds the last finished day and a run with the same start continues there.

**Never stored** (DESIGN §2.1): names, emails, the contact object, the participants, comments, recordings, voicemails, transcriptions, asset and short URLs, the other party's number (only its keyed hash), the webhook token and the API key. The user and the line are kept as ids; a line's own digits are the company's number.

**People.** `aircall-users.mjs --via-owners <HubSpot token secret>` matches each Aircall user's email to a HubSpot owner's email (in memory only) and prints, per match, the statement that puts the Aircall user id on the person who already holds that owner id (PROD_RUNBOOK 7.6, 8.7); without `--via-owners` one statement per user by email, as `hubspot-owners.mjs`. Both honour `--also-domain`, and list on stderr the Aircall user ids not matched (ids only) for Team → People → Linked accounts.

**Replay in dev.** There is no Aircall sandbox, so dev receives replayed fixtures (DESIGN §6.6): a dev connection with an invented signing secret (the token the replay puts in the body) and an invented token secret, and the setting `{"replay": true}`. The read-back then takes the call from the replayed event's own object, held in memory for that request only, with the event's time as its version (so an event replayed out of order is stale), and nothing calls Aircall (no catalogs, the reconcile lists nothing, the backfill refuses with `replay_connection`). Honoured only when the environment holds `INGEST_ALLOW_REPLAY=1`, which `deploy.sh dev` sets on the service and the jobs and `deploy.sh prod` never sets: in prod the setting does nothing and the call is read from Aircall's API. An event of a replay connection that the sweep picks up has no object any more and fails `replay_payload_gone`. `tools/replay.mjs` refuses a `--url` whose host is not the local machine or a `run.app` address (prod is reached through its public front and its `run.app` address refuses everyone, so `run.app` means dev) unless `--allow-host` insists, with a warning (since 17 October 2026).

## Shopify

The Shopify adapter (briefs B10 and B10.1; DESIGN §2, §2.1, §4.3, §4.3a, §6; additions 0008g and 0008h), `ingest/src/adapters/shopify/`. The prod sequence is `docs/ingest/PROD_RUNBOOK.md` phase 9; this section is what each step relies on.

**Shopify's rules, checked on shopify.dev on 13 October 2026** (the pages: `shopify.dev/docs/api/usage/versioning`, `…/apps/build/webhooks`, `…/apps/build/webhooks/verify-deliveries`, `…/apps/build/webhooks/troubleshoot`, `…/apps/build/authentication-authorization/client-credentials-grant`, `…/apps/launch/protected-customer-data`, `…/apps/build/apis/graphql-admin/rate-limits`, `…/api/usage/access-scopes`):

- **API version.** `2026-10` is the latest stable version (released 1 October 2026, supported until 16 October 2027; `2027-01` is the release candidate). It is pinned as the default; a connection setting `api_version` overrides it. Shopify releases quarterly and supports a version for at least 12 months, so the setting moves once a year.
- **Delivery.** "Shopify has a one-second connection timeout and a five-second timeout for the entire request"; any answer other than 2xx, a redirect included, is a failure. "If Shopify receives no response or an error, it retries 8 times over the next 4 hours. After 8 consecutive failures, the subscription is automatically deleted if it was configured using the Admin API", and Shopify emails the app's emergency developer address. Deliveries are not in order and can arrive late (up to a day); Shopify recommends a reconciliation job, which the nightly reconcile is.
- **Headers.** `X-Shopify-Topic`, `X-Shopify-Hmac-Sha256`, `X-Shopify-Shop-Domain`, `X-Shopify-API-Version`, `X-Shopify-Webhook-Id`, `X-Shopify-Triggered-At`, `X-Shopify-Event-Id`. Shopify's duplicate key is `X-Shopify-Webhook-Id` (the same on every retry of a delivery); `X-Shopify-Event-Id` is shared by every delivery one merchant action causes. The CMA keys events by the webhook id (below), a deviation from DESIGN §2, which named the event id before this was checked.
- **HMAC.** Base64 HMAC-SHA256 of the raw body with the app's client secret. After a rotation of the client secret Shopify may sign with the old one for up to an hour; a delivery the service refuses in that hour (401) is retried by Shopify (eight times over four hours), so a rotation loses nothing once the new secret is the latest version in Secret Manager (the service reads it within five minutes).
- **Token.** Apps of the Dev Dashboard use the client credentials grant: `POST https://<shop>/admin/oauth/access_token`, form-encoded `grant_type=client_credentials`, `client_id`, `client_secret`; the answer is `{access_token, scope, expires_in}` with `expires_in` 86399 (24 hours), no refresh token (mint again). It works only for stores in the app's organisation (`shop_not_permitted` otherwise).
- **Protected customer data.** Level 1 is customer data without the protected fields; Name, Email, Phone and Address are requested one by one (Level 2). For a custom-distribution app both levels are "always available" (selected, not reviewed). A field the app is not granted is `null` in GraphQL (with an `ACCESS_DENIED` entry in `errors`) and redacted in webhook bodies. In Pulse4all's Dev Dashboard (14 October 2026) there was nothing to select: the custom-distribution app got every customer field (name, email, phone, address, device data) and the store owner's staff data automatically, so minimisation rests on what the adapter reads (of the protected fields, email and phone only) and on the client secret (README Decision log, 14 October 2026). Shopify still withholds the order's own `phone`: `CmaOrders` answers with a partial `ACCESS_DENIED`, which `client.mjs` reads as an empty field; the Dev Dashboard counts those answers as errors (about 51% for the NL store), the orders are complete. Since API version 2025-01 customer webhooks no longer carry the order count and amount spent, which is why the adapter reads the customer with every order (below).
- **Rate limit.** GraphQL is limited by query cost per app and store: a bucket that refills at the plan's restore rate (standard 100 points a second, Advanced 200, Plus 1,000, Enterprise 2,000), one query at most 1,000 points; every answer carries `extensions.cost.throttleStatus`. `read_orders` covers the last 60 days; older orders need `read_all_orders`, which the Dev Dashboard did not offer on 14 October 2026 and which has no API access requests page to ask for it (README Open decisions).

**Setup, once per app and per store** (PROD_RUNBOOK 9.1 to 9.8): the app's client secret into Secret Manager (`ingest-shopify-app-signing`, granted to the service); per store the connection (`upsert_connection('shopify', <name>, '<handle>.myshopify.com', 'ingest-shopify-app-signing', null)`, kind `commerce`), its settings (`client_id`, `api_version`, `shop_handle`, `crm_connection_id`), its store row with market, currency and zone, the renewal settings for its subscription app, the subscriptions by `shopify-subscribe.mjs`, the backfill.

**Per delivery** (one object per request): the HMAC of the raw body against the signing secret, compared in constant time (`crypto.timingSafeEqual` on the two base64 strings; another length is a failure); a failure is `401`, empty, nothing written. The event is recorded as `sh:<X-Shopify-Webhook-Id>` (without it `sh:<topic>:<X-Shopify-Event-Id>`, else a digest of the body), ids, the topic, the trigger time and the API version only, never the body. A delivery whose `X-Shopify-Shop-Domain` is not the connection's account is recorded as `ignored` with `portal_mismatch`; a topic other than the seven as `ignored` with `event_not_handled`. Kinds: `customers/create`, `orders/create` → `created`; `customers/update`, `orders/updated`, `orders/cancelled` → `changed`; `customers/delete`, `orders/delete` → `deleted` (no read: marked deleted at the event's time, the phone hash cleared). Then, within the route's own budget (`INGEST_SHOPIFY_READBACK_BUDGET_MS`, default 1500 ms, well inside Shopify's five seconds), the object is read back and written; what the budget does not cover fails for the sweep a minute later.

**Read-back** (`read.mjs`): orders by `nodes(ids)`, five a call: name, times, cancellation, test, currency and the five amounts, financial and fulfilment status, `sourceName` and the app's id (what the renewal settings name), tags, the visit that brought the order (`customerJourneySummary.firstVisit`, else `lastVisit`: the landing page reduced to host and path, the five UTM tags, the referrer's host), the first ten line items (the rest paged a hundred at a time, at most 500) and the order's customer with the customer's own fields. Then the prior order count, 25 orders a call: the customer's `numberOfOrders` minus `ordersCount(query: "customer_id:<id> AND created_at:>='<created>'")` (this order included), exact when Shopify's count is `EXACT`; when the search does not hold the new order yet (a count of 0), the order is written with `order_kind` unknown and its next read (an `orders/updated` delivery, the reconcile) counts again. Customers by `nodes(ids)`, fifty a call, unless an order of the batch brought them: state, locale, `numberOfOrders`, `amountSpent`, times, and in memory `defaultEmailAddress` and `defaultPhoneNumber` (Shopify deprecated the customer's `email` and `phone` fields). A customer or order Shopify no longer has finishes `ignored`.

**The phone** (addition 0008g; Decision log, 13 October 2026): the order's own `phone`, else its customer's `defaultPhoneNumber` (never a billing or shipping address phone: the adapter does not read addresses, although Shopify grants them; whether to read the shipping address's phone as a fallback is a README Open decision, Indirect sales), hashed with the tenant's pepper and the store's market as the default region, exactly as a call's other party (`src/core/hash.mjs`), into `phone_hash` on the order and on the customer; the number is dropped. When the store withholds Phone, the hash is null and nothing fails. Shopify withholds the order's own `phone` (above), so in practice an order's hash is its customer's: 339 of 501 orders of the NL store carried one on 14 October 2026. Without the tenant's pepper nothing is read (`pepper_unavailable`).

**The match, kept in the CMA** (`match.mjs`; addition 0008h; README Decision log, 13 October 2026): every customer read (on its own or with an order) is matched once per batch to a contact of the CRM connection named by the setting `crm_connection_id`, stopping at the first that answers: (1) known: the customer's link in the CMA (`commerce_customer.crm_contact_source_id`) to a contact of that connection, checked to still exist as itself by one batch read of every linked contact of the batch (the object id only; a contact deleted or merged into another is not there, and the customer goes on to the next steps), then the contacts the CMA holds whose refs hold the customer id (no CRM call either way, so repeat and renewal orders cost no search); (2) the customer's email, searched in the CRM (exact, lower case), then dropped; (3) when the store withholds Email: the contacts whose ref properties hold the customer id (the CRM connection's contact ref fields for `shopify`, `cma.set_connection_field(<CRM conn>, 'contact', 'ref', 'shopify', <property>, <slot>)`). Exactly one contact → the link set by `cma.set_commerce_customer_contact` (`linked`, `relinked` or `unchanged`; `matched_at` is the time of the match); none or several → the link cleared (`cleared`, or `unlinked` when there was none), counted as `match_none` or `match_several` in the `processed` log line (no ids). A deleted customer's link is cleared with its deletion (no read), and the CRM's privacy deletion of a contact (the HubSpot adapter's forget) clears every link to it (`cma.forget_commerce_contact_links`). **Nothing is written to the CRM**: the HubSpot–Shopify app writes the Shopify contact fields and creates a Self Serve deal per new order, one writer per property; no outbox action is enqueued. The searches keep to one per 400 ms per CRM connection and process (HubSpot allows five a second); a webhook never waits past its budget for one (`paced`, the sweep reads it). A CRM that cannot answer fails the event with `crm_<code>` and the sweep tries again. A store without `crm_connection_id` leaves its links as they are (`match_not_configured`).

**Pacing** (`client.mjs`): one cost-bucket estimate per shop and process, from Shopify's standard plan (1,000 points, 100 a second) until the shop's first answer, then the shop's own `throttleStatus`. A call takes its estimated cost before it is sent (the estimate may go below zero, so a burst queues). The webhook path waits for points only while a second of its budget is left for the call, else the event fails `throttled` and the sweep reads it; the jobs wait for the refill. A `THROTTLED` answer or a 429 empties the estimate and fails `rate_limited`. A renewal run's burst of orders is therefore answered at once (the flow verifier's burst of 200: every answer within a second) and read by the sweep within the bucket. One token per connection and app is minted for the whole process and burst and cached until five minutes before it expires; a 401 drops it. The cache is keyed by the connection, its secret name and the client id, never by the shop alone (CMA-037 item 1, the IT audit of 17 October 2026): a connection of another tenant naming the same shop and client id, both public values, reads its own secret and mints its own token, and a missing secret fails its reads with `client_secret_unavailable` instead of riding on the first tenant's token (`verify/shopify-client.mjs`, `verify/shopify-flow.mjs` section L2).

**Reconcile, backfill and the subscription check** (`reconcile.mjs`): reconcile lists `customers` and `orders` with `updated_at` in the look-back (26 hours), sorted by `UPDATED_AT`, 100 a page, ids and times only; each becomes a synthetic event `sync:<type>:<id>:<updatedAt>` on the webhook's read-back, so an unchanged object is read once. Then the subscription check (sync_run `subscriptions_check`): the shop's `webhookSubscriptions` whose address ends in `/shopify/<connection key>`; all seven there → nothing; some missing (Shopify deletes a subscription after eight failed deliveries) → created again at the address of one that remains and the run's error is `subscriptions_recreated`, so it is seen; none left → `subscriptions_missing` (run `shopify-subscribe.mjs`; the job does not know the public address). Deliveries missed while a subscription was gone are covered by the 26-hour look-back. Backfill: `--object commerce_customer` or `commerce_order` from `intake.start_date` (or `--from`), `created_at` ascending, resumable from the cursor `backfill:<type>` after every page.

**Never stored** (DESIGN §2.1): names, email addresses, phone numbers (only the keyed hash), postal addresses, notes, the landing page's query beyond the five UTM tags, the referrer beyond its host, the client secret and the token. The flow verifier greps every database row of its run (the audit log included) and every log line for the fixture emails and numbers.

**The subscriptions** (`docs/ingest/shopify-subscribe.mjs`, run from Cloud Shell with your own gcloud login; the client secret is read from Secret Manager into memory and the token is minted for the run, neither printed):

**Terminal** (in `~/cma`; `<key>` is the store connection's key)
```bash
node docs/ingest/shopify-subscribe.mjs --project p4a-cma-prod --shop <handle>.myshopify.com --client-id <client id> --secret-name ingest-shopify-app-signing --url "https://ingest.pulse4all.app/shopify/<key>"
```
Expected: seven lines `created  gid://shopify/WebhookSubscription/<id>  <TOPIC>` (on a rerun `exists …`). `--list` prints every subscription of the shop (`*` marks the address of `--url`), `--delete <id>` deletes one, and `--source-names [--days 30]` prints the sales channels and apps of the store's recent orders with their counts (what the renewal settings name; no customer data).

## Email

The email poll (brief B17b; addition 0008m; README Data model: email activity, Decision log 15 October 2026), `ingest/src/adapters/hubspot/email-poll.mjs` with `email.mjs` (engagements), `conversations.mjs` (inbox conversations), `rules.mjs` (classification) and `owners.mjs` (the owner and account maps); the job `ingest-poll-email`, every minute. The steps in dev are `docs/b17b-email-ingest/MORNING_RUNBOOK.md`, in prod `docs/ingest/PROD_RUNBOOK.md` phase 10. Two sources, kept apart (R4): the CRM's email engagements (`crm_email`: sent from the CRM, logged by BCC, replies to logged emails) and the inbox conversations' messages (`inbox_message`). No conversation webhook: their support in a 2026.09 project app is unproven, so both are polled. No new route.

**Switched on per connection.** The poll, its reconcile and its backfill serve a HubSpot connection only while its settings hold `email_poll` (the boolean `true`), so a deploy of the job polls nothing before the app's new scopes are accepted and the connection is configured. Settings (`cma.set_connection_settings`, which replaces the whole object, so merge the current settings in):

| Setting | What | Default |
|---|---|---|
| `email_poll` | `true`: the email poll serves the connection | off |
| `email_thread_property` | the engagement property holding HubSpot's thread id, stored as `thread_source_id` (refused when it holds an `@` or white space) | none: no CRM thread id |
| `email_origin_property` | the engagement property that tells whether a sequence or an automation sent the email; its value is kept in `raw` as `origin` | none |
| `email_automated_origins` | values of the origin property (comma-separated, any case) that mean an automation sent the email: such an email's actor is `system`, without an owner | none |

The two property names are read in the account, never guessed: `docs/ingest/hubspot-email-check.mjs` lists the engagement properties the ingest reads (present or not, the values of `hs_email_direction` and `hs_email_status`) and the candidates for the two settings (names and labels with thread, sequence, origin, source, logged, automation or workflow, with their option values), and counts the actor id prefixes (below), and lists the inboxes and channels:

**Terminal** (in `~/cma`)
```bash
node docs/ingest/hubspot-email-check.mjs --project p4a-cma-dev --token-secret ingest-hubspot-dev-token --days 30
```
Expected: four blocks: `== 1.` the eight properties, each `present` (or `MISSING`), `hs_email_direction` with `options: EMAIL, INCOMING_EMAIL, FORWARDED_EMAIL`, `hs_email_status` with its options; `== 2.` the candidates (name, label, type, options); `== 3.` lines `<prefix> <type> <count>`; `== 4.` the inboxes and channels with their ids and names (a name holding an address is not shown), for `cma.set_inbox` and `cma.set_inbox_channel` before the first poll. Names and labels of properties are metadata; no email, contact, owner or actor id, name or address is printed.

**Engagements** (`email.mjs`). `POST /crm/v3/objects/emails/search` by `hs_lastmodifieddate`, ascending, 100 a page (scopes `crm.objects.contacts.read` and `sales-email-read`), from the cursor `email:engagements` (`{at}`: the newest modified time written; on the first poll the last 26 hours, not before the email start); the cursor moves after every page written. Properties asked for: `hs_timestamp`, `hs_email_direction`, `hs_email_status`, `hubspot_owner_id`, `hs_createdate`, `hs_lastmodifieddate`, the two configured ones, and only while the connection has an active rule of that kind `hs_email_subject` (subject rules) or `hs_email_from_email` (sender domain rules); never the text, html, headers, recipients or attachments. Mapping: `EMAIL`, `INCOMING_EMAIL`, `FORWARDED_EMAIL` → `out`, `in`, `forwarded` (another value: skipped); `hs_email_status` → its value in lower case when that is `sent`, `bounced`, `failed` or `scheduled`, else `other`; the actor: incoming → `customer`; an automated origin → `system`; with an owner → `agent` with `owner_ref` the owner id; else `unknown`. Then the associations email → contact, deal and ticket (v4 batch read, stored in their one direction as `crm_email` → …; read with each new or changed email, so an association added later without a change to the email arrives with its next change), the email's contact (labelled primary, else the lowest id) on the row, and last the contacts the page's emails point to that the CMA has no row for yet, read with every configured contact property (R6: `cma.ingest_upsert_contacts` holds a contact only once an email or thread points to it). An email the CMA holds at the same version is not written again (every update would be an audit row; the poll's boundary and the reconcile list most emails twice). Deletions of engagements are not seen (a search lists live objects only, and the app subscribes to no email webhook); a contact's privacy deletion clears it from emails and threads (0008m).

**Inbox conversations** (`conversations.mjs`; scope `conversations.read`; paths under `/conversations/v3/conversations`):

- Catalogs at most hourly per connection (cursor `email:catalogs`): `inboxes` (id and name; an archived inbox is left out, so the database archives it; a name holding an `@` is replaced by the id) into `cma.connection_inbox`, `channels` (id, name and a canonical kind from the name: email, chat, whatsapp, messenger, form, phone, sms, other) into `cma.connection_inbox_channel` (a new channel takes the tenant's channel keyed as its kind and counts only as `email`; configuration from then on), `channel-accounts` (id → inbox id, kept in the cursors `email:accounts` and `email:accounts:<n>`; their names and delivery identifiers, which hold the mailbox's address, are not read). A message's inbox is its channel account's, else its thread's.
- The owner map at most hourly (cursors `email:owners`, `email:owners:<n>`): `GET /crm/v3/owners`, archived and active (`crm.objects.owners.read`), user id → owner id; ids only, the owners' names and emails dropped. Each job run is a new process, so the maps live in `cma.sync_cursor` in parts under its 2 kB limit; no table.
- Threads: `GET threads?sort=latestMessageTimestamp&latestMessageTimestampAfter=<cursor>&association=TICKET`, 100 a page. HubSpot needs `latestMessageTimestampAfter` with that sort and then answers ascending (the spec's `sort` parameter, `PublicApiSpecs/Conversations/Conversations Inbox & Messages/Rollouts/54902/v3/conversationsInboxMessages.json`). The cursor `email:threads` (`{at, ids}`: the newest latest-message time written and the threads at it, which the next page leaves out) moves after every page. A thread's row: inbox, original channel, status, close time, the assignee's owner id (an agent only), the contact, the ticket (with `association=TICKET`), spam, archived, the latest received and sent times, the read's time as its version; written when it changed (a thread held exactly so is not written again).
- Messages: per changed thread (its latest message newer than where the CMA's stored messages and events stand, `cma.ingest_thread_marks`) `GET threads/{id}/messages`, paged, kept after that mark. `MESSAGE` → `cma.email_message` (`INCOMING`/`OUTGOING` → `in`/`out`; status `failed` when HubSpot says so, `sent` for an outgoing one, `other` for an incoming one; the thread's contact); `ASSIGNMENT` → `assigned` (to the agent's owner id; no assignee: an unassignment), `THREAD_STATUS_CHANGE` → `closed` or `reopened`, `THREAD_INBOX_CHANGE` → `moved_inbox` with both inbox ids, into `cma.email_thread_event`; every other type (comments, welcome messages) is ignored. A thread's category is its first message's, when the CMA reads it.
- The open check every ten minutes (cursor `email:open-check`): the source's open threads (`threadStatus=OPEN`) against the CMA's. A held thread whose status, agent, inbox, channel, contact, ticket, spam or archived state differs, or that the CMA holds open while the source does not list it open, is read again by id with its messages after the mark, in case a close or a reassignment without a new message does not move its latest message time (to see in dev, runbook step 6).
- Gone: a held thread the source no longer has (404 by id, also with `archived=true`, or on its messages) is a conversation's deletion at the source, and `cma.ingest_thread_forget` runs: the thread and its messages keep ids, times and kinds and lose the contact, the ticket and raw; a later read cannot bring them back.
- Spam threads are stored with `is_spam`; archived ones (the source's trash) with `is_archived`.

**Actors (R2).** Only the actor's kind is stored, and for an agent the owner id; never `createdBy`, `assignedTo` or `assignedFrom` as such (an email actor's id holds the address). HubSpot's spec types the actors `AGENT`, `BOT`, `INTEGRATOR`, `SYSTEM`, `VISITOR`, `EMAIL` and `LLM` and does not document their ids' prefixes. The adapter maps by prefix:

| Prefix | HubSpot's type | CMA actor kind | Confirmed |
|---|---|---|---|
| `A-<user id>` | `AGENT` | `agent`, owner id through the owner map (none when the user is no owner) | yes: the live portal, 16 October 2026 |
| `V-` | `VISITOR` | `customer` | yes: the live portal, 16 October 2026 |
| `E-<address>` | `EMAIL` | `customer` | not seen yet |
| `S-` | `SYSTEM` | `system` | yes: the live portal, 16 October 2026 |
| `B-` | `BOT` | `bot` | not seen yet |
| `I-` | `INTEGRATOR` | `integration` | not seen yet |
| any other (the `LLM` actor's among them until block 3 shows it) | | `unknown` | |

The prefixes are the ones README's Data model: email activity names from HubSpot's guides. Block 3 of `hubspot-email-check.mjs` showed `A AGENT`, `S SYSTEM` and `V VISITOR` in the live portal's 200 threads of the last 30 days on 16 October 2026 (`PROD_RUNBOOK.md` 10.2, `records/b17b-prod-2026-10-16`); `CMA dev` had no conversation at its step 3a, and its overlap test (step 6) then gave the kinds `customer`, `agent` with an owner and `system` (`records/b17b-dev-2026-10-16`). `E`, `B` and `I` keep the prefixes of the guides until a later block 3 shows them, which marks them here (Martin's report). A prefix block 3 shows for `LLM` becomes the kind `ai` in `ACTOR_PREFIXES` (`conversations.mjs`), one line.

**Rules (R1).** The classification rules (`cma.connection_email_rule`, from `cma.connection_config` in their order) are applied in memory by `rules.mjs` with the words logic of `cma.email_words_match` (contains any word and none of the exclude words, case-insensitive): the subject of an engagement or a message, the domain of the sender's address (an engagement's `hs_email_from_email`, a message's first sender whose delivery identifier is an email address). The value matched lives for that call only; only the category code is written. The database stays the definition: `verify/email-mapping.mjs` and `verify/email-flow.mjs` run the same fixtures (`ingest/verify/fixtures/hubspot/email-rules.json`) through the code and through `cma.email_words_match` and `cma.email_category_of`.

**A failed read** (429, a timeout, a scope not yet accepted) stops that part (engagements or conversations) without moving its cursor; the other part still runs; the run's `sync_run` row fails with the first part's code and the next run reads again. A run stops starting new pages after 40 seconds, so runs every minute do not pile up; the cursors carry the rest. Pacing as every HubSpot job: one call per 200 ms, a search per 400 ms (half of HubSpot's documented limits).

**Reconcile and backfill.** With the email poll on, the nightly reconcile adds `crm_email` (engagements modified in the look-back, written as the poll writes them; an unchanged one is not rewritten) and `inbox_thread` (threads whose latest message falls in the look-back; then the source's trash, `archived=true`: a held thread there is marked archived, a held archived thread found neither there nor by id is forgotten, one restored is written as it is). The backfill takes `--object crm_email` (by `hs_timestamp`, cursor `backfill:crm_email:hs_timestamp`) and `--object inbox_thread` (by latest message, with the messages, cursor `backfill:inbox_thread`), both from `cma.email_start_date_of` (`email.start_date`, else `intake.start_date`) unless `--from`, resumable after every page; `--object contact` reads every held contact again (now also those an email or thread points to) with every country slot.

**Contacts' country** (0008m): every configured country slot of the contact is read; one slot is sent as `country`, as before, two or more as `countries` (the value of slot n at element n − 1), and the database keeps the first that names a catalog market, else the first value as written, with the slot in `country_source`. A record's fallback market (no market property mapped) is the first non-empty slot; its market at query time falls through to the contact's stored country (0007d).

**Logs** (R5): per connection one line `poll-email: connection` with the run's counts and the outcomes per kind (`emails`, `threads`, `messages`, `events`, `contacts`, `associations`, `forgotten`), and a warning per failed part with the part's name and the code. Never an email, thread, message, contact or actor id, a subject, an address or a name.

## Trusted Shops

The Trusted Shops adapter (brief B18; addition 0008ze, `docs/architecture/data-model/0008.md`, Data model: reviews), `ingest/src/adapters/trustedshops/` (`client.mjs`, `read.mjs`, `map.mjs`, `match.mjs`, `reconcile.mjs`, `index.mjs`), reads the reviews of a business line's Trusted Shops account through the eTrusted API into `cma.review_channel` and `cma.review`. The prod sequence is `docs/ingest/PROD_RUNBOOK.md` phase 13; this section is what each step relies on. Read only: nothing is written to eTrusted or to the CRM.

**No route.** A review platform sends no webhook, so the adapter is of kind `poll` and the server answers `404` on `/trustedshops/<connection key>`, as for an unknown adapter. A review reaches the CMA only through the poll, the reconcile and the backfill.

**What it reads** (`read.mjs`). `GET /channels`: the account's channels (id `chl-…`, name, locale). `GET /reviews?channels=<id>&submittedAfter&submittedBefore&count=100[&after=<review id>][&ignoreStatements=false]` per channel: cursor paging by review id (the answer's paging cursor `after`, else the last item's id) until a page holds fewer than asked. The answer's `totalElements` is never read (the prod discovery of 25 October 2026 saw 0 next to 10 items). `ignoreStatements=false` asks for the star-only reviews (statements) too, which the API leaves out otherwise (setting `etrusted_include_statements`, default true). The page size 100 and the cursor field are confirmed in practice on 25 October 2026 (845 reviews, 7 channels, 60 requests a minute, no 429). **Still to confirm on the live account:** `ignoreStatements` and the rate limits; the parameter names follow the prod discovery and the developer reference as far as it could be read on 25 October 2026.

**Authentication** (`client.mjs`). OAuth2 client credentials: `POST https://login.etrusted.com/oauth/token`, form-encoded `grant_type=client_credentials`, `client_id` (the connection setting `client_id`, not a secret), `client_secret` (the secret the connection's access secret name points to, in Secret Manager) and `audience=https://api.etrusted.com`; then `GET https://api.etrusted.com/<path>` with the bearer token. The token lives 300 seconds and is cached until 30 seconds before it expires (half its life when shorter), keyed by the connection, its secret's name and the client id, as the Shopify client is (CMA-037): a connection of another tenant never rides on the first tenant's token, and a missing secret fails its reads with `client_secret_unavailable`. One mint however many ask at once; a 401 drops the token. No redirect is followed, so the secret goes to the login host only. An error carries a code only, never a body: `client_id_not_set`, `client_secret_unavailable`, `token_http_<status>`, `token_invalid`, `token_timeout`, `token_unreachable`, `rate_limited`, `http_<status>`. Connection settings refuse a key that contains "secret", so the client's secret lives only in Secret Manager, named by the connection's token secret name (`cma.upsert_connection('trustedshops', <name>, <account id>, null, <access secret name>)`: no signing secret, there is no webhook).

**The API client** (Pulse4all Subscriptions, prod). It exists: Martin created it on 25 October 2026 during the discovery, in the eTrusted Control Centre → Settings → SSO-clientbeheer (the Dutch interface's name for API client management): name `CMA prod ingest`, identifier `CMAprodIngest`, client id `<prefix>__CMAprodIngest` (written into the connection's settings, never into the repository). It took the account's last free client slot (5 of 5): no other client is created. An eTrusted API client has no scopes, so this one can read and write (invites, replies, vetoes); the adapter only reads, and only `cma-ingest` can read its secret from Secret Manager. The secret is not shown only once: the client's row → the arrow → **Tonen** shows it again (PROD_RUNBOOK 13.5).

**Settings** (connection settings, `cma.set_connection_settings`, which replaces the whole object, so merge the current ones in; or Configuration → Sources → the connection → Settings):

| Setting | What | Default |
|---|---|---|
| `client_id` | the API client's id | none: the run fails `client_id_not_set` |
| `crm_connection_id` | the CRM connection the reviewers' emails are looked up in (below) | none: no contact match, the order link still works |
| `reviews_poll_interval_minutes` | how often the poll reads (1 to 1440) | 60 |
| `reviews_reconcile_days` | how many days back the nightly reconcile reads, and the first poll of a channel (1 to 365) | 30 |
| `etrusted_max_per_minute` | the adapter's own pace on eTrusted's API, per connection and process (1 to 600) | 60 |
| `etrusted_include_statements` | `true`: star-only reviews are asked for too; `false`: left out | true |
| `transaction_ref_pattern` | the pattern a review's transaction reference must fit to be kept (addition 0008zf). **Pacing.** eTrusted's rate limits are not documented (to confirm on the live account), so the adapter keeps to `etrusted_max_per_minute` (the default 60 a minute met no 429 over the first backfill's 845 reviews and 7 channels): one pace per connection and process, shared by the poll, the reconcile and the backfill. A 429 holds the connection until its `Retry-After` (at most two minutes; one minute without it) and fails the call `rate_limited`: the run ends where it stands, the cursors of the channels already read have moved, and the next run carries on. Nothing retries in a loop. Every request is counted per endpoint (`GET /channels`, `GET /reviews`, `POST /oauth/token`, ids replaced) in the run's log line.

**Poll** (`ingest-poll-reviews`, hourly at minute 7, Europe/Amsterdam). Per active connection of the adapter and due on `reviews_poll_interval_minutes` (cursor `reviews:cadence`; a connection not due writes nothing), one `sync_run` row (job `reviews_poll`, stream `reviews`): the channel catalog first (`cma.ingest_upsert_review_channels`; a new channel lands without a market and not counted), then per channel in id order the reviews submitted after the channel's cursor (`reviews:<channel id>`, the start of the last poll that walked it) less two hours, since a review can reach the API after its submission time; a channel without a cursor starts `reviews_reconcile_days` back. Each page is mapped, upserted (`cma.ingest_upsert_reviews`: the stale guard, the order link), the alerts are raised for what was written (`cma.ingest_review_alerts`, before the contact lookups, so a pause in them costs no alert), and the contacts of the new reviews without a link are looked up. A poll never pauses: below the CRM's daily floor it stops the lookups and goes on. The run's counts are `fetched` (reviews read), `upserted` (inserted or updated), `stale`, `skipped` (unchanged, unreadable, or of a channel the catalog lacks), `failed` (lookups that failed) and `ref_dropped` (reviews whose transaction reference was left out, present only above 0; the reconcile and the backfill count it the same way); the log line `poll-reviews: connection` has the details.

**Reconcile** (`ingest-reconcile`, 03:30). The reviews submitted in the last `reviews_reconcile_days` (default 30, or the job's look-back when that is longer) read again: a changed state, a reply, a veto; every review still without a link is looked up again. The CRM's daily floor pauses it, as HubSpot's jobs (section API budget).

**Backfill** (`ingest-backfill --object review [--from <date>] [--again]`). Without `--from` it starts at `reviews.history_start_date` and, when that is empty, reads all history: from 1 January 2000, before the platform held a review, in windows of one year. Per channel in id order and oldest first, resumable (the cursor `backfill:review` holds the start, the channel, the next window and whether it is done, and a run with the same start continues there), paced as above. A finished backfill with the same start reads nothing again unless the run has `--again`, which walks it again; a review already stored unchanged is written nowhere. Every review without a link is looked up by email, and the CRM's daily floor pauses the run (succeeded with the error `daily_floor`; the same command later continues). Each channel ends with one summary line `backfill: review channel`: the reviews read and stored in this run, and what the channel holds (`held`, `linkedOrder`, `linkedContact`, `unlinked`, `oldestSubmittedAt`, `newestSubmittedAt`). Requests are logged per endpoint. A full backfill's time is dominated by the HubSpot contact lookups, not by the eTrusted paging (about 9 minutes for 845 reviews in prod).

**What the Control Centre counts** (platform facts, to read a comparison with Reports → Reviews). The eTrusted Control Centre counts the reviews in the states APPROVED and MODERATION and leaves out REJECTED. Its score is the simple average of the APPROVED reviews submitted in the last 12 months, and it appears to cut to two decimals, so a hundredth of difference can show. Reports → Reviews averages the selected period and counts published (APPROVED) reviews of counted channels only, so it differs from the Control Centre by design.

**Data protection** (hard rules; Decision log, 25 October 2026):
- Never store, log or put in `raw`: `customer.fullName`, `customer.email`, `customer.mobile`, `title`, `comment`. `map.mjs` is an allow list: only the fields it names are read, so anything the API adds later never reaches an item, `raw`, a log or the database.
- `raw` keeps a filtered set of metadata keys only (`id`, `channelRef`, `rating`, `type`, `state`, the times, `inviteRef`, `event.type`, `transaction.reference` when it is kept, below); the database checks it (`cma.review_raw_ok`).
- **The reference rule** (addition 0008zf; in prod a manual invite carried the reviewer's email address as its transaction reference). `transaction.reference` is kept, in the item and in `raw`, only when the connection setting `transaction_ref_pattern` accepts it and it holds no @. Otherwise it is left out of both and counted as `ref_dropped` in the run's counts (only when above 0); its value is never logged. The database refuses an @ in `transaction_ref` and in `raw` (check `review_reference_no_at`), and no audit row of a review keeps one (`cma.audit_row()`), so the adapter's drop is the first line and the check the last.
- `customer.email` is used in memory only, to find the CRM contact (the forms poll's pattern), then dropped: `map.mjs` hands it back next to the item, and the map that holds it is emptied entry by entry and before every return.
- The contact's privacy deletion clears a review's contact link (`cma.forget_review_contact_links`, called with the HubSpot adapter's forget, as 0008h does for commerce).
- Alerts and the reports show no review text and no customer data: market, channel, rating, time, link level, and a link to the review in the eTrusted Control Centre.

**The contact match** (`match.mjs`). The order comes first: in the database a review whose transaction reference names one of the tenant's orders (order name, else source id) is linked to it and to its customer's contact (0008h). A review without an order and without a contact is looked up by the reviewer's email in the CRM connection `crm_connection_id` names, through that CRM adapter's contact lookup (HubSpot: an exact search on the lower-cased email, one per 400 ms): exactly one contact gives the link (`cma.set_review_contact`, level `contact`), none or several give none. Every search is guarded by the CRM connection's daily floor (`api_daily_floor_pct`, default 25): a poll stops searching below it and counts the rest as deferred, which the reconcile looks at again; a backfill or reconcile pauses with `daily_floor`. A rate limit, a missed slot (`paced`) or a timeout stops the searches that follow on that page, which would meet the same limit. Without `crm_connection_id` nothing is looked up.

**Logs.** Per connection one line `poll-reviews: connection` with the run's counts, the details (`inserted`, `updated`, `unchanged`, `unknownChannel`, `unreadable`, `linkedOrder`, `lookups`, `contacts`, `noContact`, `severalContacts`, `lookupsDeferred`, `lookupsFailed`, `alerts`, `channels`), the requests per endpoint and the CRM lookups' daily reading; the lines `reconcile: reviews`, `backfill: review channel` and `backfill: reviews`; and a warning `etrusted rate limited` with the connection id, the code and the seconds until the calls resume. Never an email, a name, a title or a text.

**Verifiers:** `verify/reviews-mapping.mjs` and `verify/reviews-flow.mjs` (section Verifiers), both against the fake eTrusted `verify/etrusted-fake.mjs`; each fails every check when provoked.

## Airtable

The Airtable adapter (addition 0008zj, `db/114_asset_sync.sql`; `docs/architecture/data-model/0008.md`, Data model: asset sync), `ingest/src/adapters/airtable/` (`client.mjs`, `read.mjs`, `map.mjs`, `index.mjs`), reads a business line's asset register from its Airtable base through the Airtable Web API into `cma.device` and `cma.device_component` with 0008zi's load: since addition 0008zk (`db/116_asset_sync_load.sql`) the rows a read maps are loaded in chunks by `cma.ingest_load_device_chunk`, the set-based load `cma.load_device_snapshot` also runs for a file (`cma.device_rows_apply`), and a full snapshot ends with `cma.ingest_mark_devices_missing` in slices (The load, below); the mapping is by field id. The prod sequence is `docs/ingest/PROD_RUNBOOK.md` phase 14; this section is what each step relies on. Read only: nothing is written to Airtable. The register owns its devices and the CMA mirrors them; the CSV import (`docs/import/devices.md`) stays as the fallback.

**No route.** Airtable's webhooks only ping (the payloads are fetched separately) and a webhook made with a personal access token expires after seven days, while minute-level freshness is enough for maintenance planning, so the adapter polls (Decision log, 27 October 2026): kind `poll`, and the server answers `404` on `/airtable/<connection key>`, as for an unknown adapter.

**What it reads** (`read.mjs`). Before every read, `GET /v0/meta/bases/{base}/tables`: the base's tables and fields (id, name, type), against which every mapped field is checked by its id (addition 0008zk). A field renamed in Airtable keeps its id and changes nothing. A field the table lacks (deleted) fails the run with `unknown_field`, and the log line `airtable unknown field` names the field's id; a field whose type differs from the type the connection recorded when it first read it fails `field_type_changed`, and the log line `airtable field type changed` names the field (its id and name) and both types; a property that is no field id fails `field_not_an_id` (`airtable mapping not by field id`). Never a value. A table that is not there fails `unknown_table`. Then `GET /v0/{base}/{table}?pageSize=100&cellFormat=json&returnFieldsByFieldId=true&fields[]=<each mapped field id>[&filterByFormula=…][&offset=…]`: offset paging until a page carries no offset, each record's fields keyed by id. `fields[]` lists the mapped fields only, so a field the mapping does not name (the customer's names and email, who changed the row last, a note) never leaves Airtable, whatever a view hides or shows. A field the API leaves out of a record is empty (Airtable leaves empty fields out): its column is empty in the row, never left out, so the load writes it empty rather than keeping the device's earlier value. A record's id is the API's `record.id`, the same `RECORD_ID()` the CSV export carried as its record id column, so the API and the file load the same devices.

**No view** (Decision log, 28 October 2026). An asset register is read whole: a view's filter would make every device outside it look missing to the nightly full snapshot. `cma.set_connection_settings` refuses `view_id` on an asset register (CMA04), `116` removed one stored before, and the adapter never sends one (a stored `view_id` is named once in the run's log, `view_ignored`).

**Paging expiry.** Airtable lets a list's offset expire (a read that pauses too long, a server restart) and answers `422 LIST_RECORDS_ITERATOR_NOT_AVAILABLE`: the call fails `paging_expired` (the client reads that error type and nothing else of the body), the run fails before it loads anything (a full read reads every page before its first chunk), so nothing is marked missing and the cursor stays, and the next run reads from the first page again (`airtable paging expired` in the log, with how many records it had read). A nightly reconcile that fails so is caught up by a backfill or the next night. The poll's filter is `IS_AFTER(LAST_MODIFIED_TIME(), DATETIME_PARSE("<cursor less five minutes>"))`; `LAST_MODIFIED_TIME()` moves when a field of the record is edited, not when a value a lookup draws from another table changes, which the nightly full snapshot catches.

**Authentication** (`client.mjs`). A bearer token: the personal access token of an Airtable service account (Enterprise Scale), read-only on the one base, with the scopes `data.records:read` and `schema.bases:read` (Decision log, 27 October 2026). The token lives in Secret Manager, in prod only, named by the connection's token secret name (`cma.upsert_connection('airtable', <name>, <base id>, null, <token secret name>)`: no signing secret, there is no webhook), readable by `cma-ingest` only; dev never holds a real token, and the adapter is proven against a fake Airtable (`verify/airtable-fake.mjs`). A secret that cannot be read fails the read with `token_unavailable` before anything is sent. No redirect is followed, so the token goes to `api.airtable.com` only. An error carries a code only, never a body: `token_unavailable`, `rate_limited`, `paging_expired`, `unknown_field`, `field_type_changed`, `unknown_table`, `http_<status>`, `timeout`, `unreachable`, `bad_response`; and before any request `mapping_not_set`, `field_not_an_id`, `table_id_not_set`, `base_id_not_set`.

**A connection without a token secret name** is CSV-only (Decision log, 27 October 2026): `ingest-poll-assets` and `ingest-reconcile` skip it with one log line (`poll-assets: connection skipped` or `reconcile: connection skipped`, code `csv_only`) and no `sync_run` row, the backfill refuses it, and the database refuses the ingest's calls for it (`cma.ingest_load_device_chunk`, `cma.ingest_mark_devices_missing` and 0008zj's `cma.ingest_load_device_snapshot`: CMA04), so the dev fixture connection of `docs/import/devices.md` stays valid and is still loaded from files.

**The mapping** (`map.mjs`): configuration, the import's map file of 0008zi carried over to the connection's fields (`cma.set_connection_field` on the asset register connection; Configuration → Sources lists them read-only), each property the Airtable field's id (`fld…`, since addition 0008zk). The ids are generated from the live schema: the dry run lists the table's fields with their ids, names and types, and `docs/ingest/airtable-fields.mjs` turns that list and the map file's headers into the Studio statements (PROD_RUNBOOK 14.5); a header the table lacks, or one that names two fields, stops it with the header named.

| Entity | Field | `ref_system` | Feeds |
|---|---|---|---|
| `device` | `serial`, `model`, `status`, `country`, `warehouse_ref`, `customer_ref`, `subscription_ref`, `order_ref`, `first_shipped_on`, `stock_received_on`, `last_shipped_on`, `warranty_until`, `end_of_life_on` | empty | the staging column of the same name |
| `device_component` | `serial`, `expires_on` | the component kind (`pads`, `battery`: the tenant's catalog) | the kind's serial and recorded expiry |
| `device` | `ref` | the id's name (`ns_internal_id`) | a named id of another system |

Slot 1 only. The database keeps device fields on asset register connections and other fields off them, and a component's kind in the catalog (CMA04). No mapping means no read (`mapping_not_set`). **Types.** The first read records each mapped field's type, in lower case, in `connection_field.source_type` (`cma.ingest_record_field_types`; `checked_at` when); a later read refuses a different type (`field_type_changed`), so a field changed from a date to text cannot silently empty the devices' dates. To accept a changed type after checking its values (a dry run), remove that field's mapping and set it again in one Run (`cma.set_connection_field` with `''`, then with its id): the next run records the new type. Mapping a field to another id clears its type as well. An allow list: only the mapped fields are asked for and read. A value is read as the CSV import's tool writes it (`tools/devices-to-staging.mjs`), so the load applies 0008zi's rules unchanged: text trimmed, a number or a yes/no as its text, a lookup's list of values joined with `, `, anything else (an error cell, an object such as a collaborator or an attachment) left out and counted as unreadable; a value holding an @ goes no further than a bare @ and is counted, as the tool does and the database does again. What an id is, which reference is dropped and which label is unmapped, the load decides: the adapter adds no rule of its own.

**Dates.** An ISO date as a date field answers (`2024-11-15`), and an ISO timestamp, such as a formula's date (`2029-11-15T00:00:00.000Z`), by its date as written. A date that arrives as text is read in the connection setting `date_format` (`dmy`, `mdy` or `iso`, as the tool's `--date-format`); without it the run fails `date_format_not_set` and the log names the field. A text date that does not read in the format is left empty and counted (`dateFailures`).

**Settings** (connection settings, `cma.set_connection_settings`, which replaces the whole object, so merge the current ones in; or Configuration → Sources → the connection → Settings). The base is the connection's account id.

| Setting | What | Default |
|---|---|---|
| `table_id` | the register's table (`tbl…`) | none: the run fails `table_id_not_set` |
| `date_format` | how a date that arrives as text reads: `dmy`, `mdy` or `iso` | none: a text date fails `date_format_not_set` |
| `assets_poll_interval_minutes` | how often the poll reads (1 to 1440) | 15 |
| `assets_load_chunk` | the rows of one chunk of a load, each chunk its own call and transaction (100 to 5,000; addition 0008zk) | 1000 |
| `airtable_max_per_second` | the poll's pace on the base, per connection and process (1 to 5) | 2 |
| `airtable_full_max_per_second` | a full read's pace (the reconcile, a backfill, the dry run), per connection and process (1 to 5) | 4 |

The database refuses an asset register's `table_id` that is no id, any `view_id` (No view, above), a `date_format` other than the three, an `assets_poll_interval_minutes` outside 1 to 1440 and an `assets_load_chunk` outside 100 to 5,000 (CMA04); the paces are the adapter's own settings, as `aircall_max_per_minute` and `etrusted_max_per_minute` are. A stored value out of range gives the default and one log line per run (`settings out of range, defaults used`, naming the setting).

**Pacing.** Airtable allows five requests a second per base and locks a base for 30 seconds after a 429; the base also serves Make, so neither pace takes all five by default. The poll keeps to `airtable_max_per_second` (default 2: its read is usually one page); a full read (the reconcile, a backfill, the dry run) to `airtable_full_max_per_second` (default 4, at most 5), one pace per connection and process. A 429 holds the connection for 30 seconds and fails the call `rate_limited`: the run stops where it stands, nothing is loaded and the cursor stays, and the next run carries on (`airtable rate limited` in the log with the connection id and the code). Nothing retries in a loop. Every request is counted per endpoint (`GET /meta/bases/{id}/tables`, `GET /{id}/{id}`, ids replaced, no query value) in the run's log line. A full snapshot of about 10,000 records is some 100 pages, half a minute at 4 a second; at the register's horizon of 50,000 (Open decisions) some 500 pages, about two minutes.

**Poll** (`ingest-poll-assets`, every 5 minutes, Europe/Amsterdam). Per active connection of the adapter with a token secret name, when due on `assets_poll_interval_minutes` (cursor `assets:cadence`; a connection not due writes nothing and asks nothing), one `sync_run` row (job `assets_poll`, stream `devices`): the schema check, the records modified after the cursor `assets:modified` less five minutes (every record when there is none yet), mapped and loaded in chunks, without the final call, so nothing is marked missing; then both cursors move to the run's start. A poll that finds nothing changed loads nothing.

**Reconcile** (`ingest-reconcile`, 03:30). The nightly full snapshot: the schema check, every record of the table (never a view), loaded in chunks, then the final step in slices, so a device the register no longer holds is marked missing (`source_deleted_at`) and comes back when it reappears; one `sync_run` row (job `reconcile`, stream `device`); the cursor `assets:modified` moves to the snapshot's start. A full read that finds no record fails `empty_snapshot` instead of marking every device missing.

**Backfill** (`ingest-backfill --connection <id> --object device [--dry-run]`). The same full snapshot on demand (job `backfill`, stream `device`); it takes no `--from`. With `--dry-run` it reads and counts and writes nothing (no load, no `sync_run` row, no cursor, no recorded type): one log line `backfill dry run` with `tableFieldList` (the table's fields: id, name and type each, never a value; the mapping step is generated from it), `fetched`, `mapped`, `fields` (mapped), `tableFields`, `dateFailures`, `valuesWithAt`, `unreadable`, `duplicates`, `unknownFields`, `typeChangedFields` and `notFieldIds` (with an unknown field, a changed type or a property that is no field id it names them and reads no record). Without a mapping it lists the fields only. The dry run is the API's equivalent of the staging tool's counts, and the first step in prod.

**The load** (addition 0008zk, in chunks; every statement under the pool's 15-second statement timeout). The rows a read maps, numbered from 2 in record id order, go in chunks of `assets_load_chunk` rows (default 1,000), each chunk its own call of `cma.ingest_load_device_chunk(connection, rows)` and its own transaction (`store.loadDeviceChunk`; `ingest.write`, the tenant's Ingest user; one call per connection at a time). The chunk size adapts to the database (Decision log, 28 October 2026): a call slower than a third of the statement timeout (5,000 ms) halves the next chunk, down to 100 rows; a chunk the timeout cancels (57014: nothing of it is written) is sent again once at half its size, and a second cancellation among those rows fails the run before its final step (`db_57014`), so nothing is marked missing. A chunk is loaded by the set-based load (`cma.device_rows_apply`) and marks nothing missing; it stages nothing, so no staged row is written, audited or cleaned up. A full snapshot (the reconcile, a backfill) ends with the final step in slices: the run's record ids sorted by their bytes (the database's collation `C`) and cut into slices of `assets_load_chunk`, each its own call of `cma.ingest_mark_devices_missing(connection, ids, from, before)` and its own transaction (`store.markDevicesMissing`), from being the slice's first id (none for the first) and before the next slice's first (none for the last). Each call marks the connection's present devices in its range whose record id is not among its ids, by a range index, so together the slices cover every device once and no call's work grows with the register (the database refuses an id outside its range: nothing is marked). The poll never makes it. A run that fails before that step (a chunk refused, a 429, an expired paging, a timeout) marks nothing missing, as before, and the chunks it loaded change nothing when the next run loads them again (each comes back unchanged), so the next run simply starts over; a run that fails within it has marked only devices it did not read. 117 holds each chunk of a first load of 50,000 (under the same adaptive rule), one chunk of 1,000 unchanged rows and each slice of the final step at 50,000 devices under half the timeout, 7,500 ms, measured on dev's shared core (Decision log, 28 October 2026), in dev and local databases (the measurements are in `docs/architecture/data-model/0008.md`, Data model: asset sync load); prod's speed is each run's own `chunk_max_ms` and `slice_max_ms` (PROD_RUNBOOK 14.7). A component kind whose mapped fields are all empty in a record is sent as an empty object, so the load closes the device's current one of that kind (`replaced_at`, no new row; its item due unknown); a kind with a field the adapter cannot read is left out, so nothing is closed on it. A chunk of 5,000 new records, the setting's largest, takes several times one of 1,000: keep the default for a first load. The CSV fallback keeps one call (`cma.load_device_snapshot` from Studio, without the ingest's timeout). The run's counts are the load's summed over its chunks as each one lands (`rows`, `inserted`, `updated`, `unchanged`, `missing_now`, `components_replaced`, `components_closed`, `unmapped_model`, `unmapped_status`, `unmapped_market`, `customer_ref_invalid`, `refs_dropped`), its phase times in milliseconds (`stage_ms` reading the chunks, `map_ms` the checks and the mapping, `upsert_ms` the devices, `components_ms` the components, `missing_ms` the final step's slices; `cleanup_ms` 0, as nothing is staged), its slowest calls in milliseconds as the ingest measures each (`chunk_max_ms`, the slowest chunk; `slice_max_ms`, the slowest slice), its adaptive chunks (`chunk_size_min`, the smallest chunk size in force; `chunk_halvings`) and `fetched`, with `upserted` (inserted and updated) and `skipped` (unchanged); a failed run keeps the counts of the chunks it loaded. `cma.ingest_sync_run_finish()` takes the load's counts since 0008zj and the phase times, `components_closed`, the slowest calls and the adaptive chunks since 0008zk.

**Data protection** (hard rules):
- Only the mapped fields are asked for: a personal field of the register never leaves Airtable, and the mapping holds no name, email, phone, address or free-text field.
- A mapped value holding an @ goes no further than a bare @ (the tool's rule; the chunk's call does it again, as the staging does for a file), and the load reads it as no id; the audit log keeps a staged row's keys only (0008zi), and the ingest's chunks stage nothing.
- Logs hold connection ids, counts, codes and field names only: never the token, a value or a record's content.

**Logs.** Per connection one line `poll-assets: connection` with the run's counts, the details (`mapped`, `chunks`, `fields`, `duplicates`, `dateFailures`, `valuesWithAt`, `unreadable`, `changedSince`) and the requests per endpoint; the lines `reconcile: devices` and `backfill: devices` (with `chunks` and `slices`) and `backfill dry run` (with `tableFieldList`); the warnings `airtable unknown field`, `airtable field type changed`, `airtable mapping not by field id`, `airtable read refused` (a date without its format, naming the field's id and name), `airtable paging expired` and `airtable rate limited`; `view_id ignored: an asset register is read whole`; `poll-assets: connection skipped` and `reconcile: connection skipped` (`csv_only`).

## Juo

The Juo adapter (addition 0008zl, brief B20, `db/118_subscriptions.sql`; `docs/architecture/data-model/0008.md`, Data model: subscriptions), `ingest/src/adapters/juo/` (`client.mjs`, `read.mjs`, `map.mjs`, `index.mjs`), reads a store's subscriptions and the events of its subscriptions from Juo's Admin API into `cma.subscription` and `cma.subscription_event`, from which `cma.subscription_payment_state_of` derives each subscription's payment state. The prod sequence is `docs/ingest/PROD_RUNBOOK.md` phase 15 (the GB pilot); this section is what each step relies on. Read only: nothing is written to Juo, and no staff JWT is used. Juo owns the subscriptions and their events; the CMA mirrors them, and HubSpot's own Juo events stay as they are.

**No route.** Juo has no webhook topic for a failed renewal (`subscription:renew-failed`), so the adapter polls (Decision log, 28 October 2026): kind `poll`, and the server answers `404` on `/juo/<connection key>`, as for an unknown adapter.

**One connection and one key per store.** Juo's keys are per store: the GB key answers 200 for `pulse4all.myshopify.com` and 401 for `pulse4all-nl.myshopify.com` (checked 28 October 2026). A connection's account id is the store's own domain, `<handle>.myshopify.com` (`X-Tenant-ID`, lower case; another form fails `tenant_id_invalid` before any request), its token secret name the store's key in Secret Manager (`ingest-juo-<handle>-key`, header `X-Juo-Admin-Api-Key`). The store: the handle (the account id up to its first dot) must be the handle of a commerce store of the same tenant (`cma.commerce_store`), whose Shopify connection holds the customers a subscription's customer id joins (`cma.commerce_customer.source_id`); there is no link column. Without such a store every read fails `store_not_configured` before a request (`cma.ingest_subscription_store`, log line `juo store not configured`), and the database refuses the connection's writes (CMA04). A connection without a token secret name is not read: `ingest-poll-subscriptions` and `ingest-reconcile` skip it with one log line (code `key_not_set`) and no `sync_run` row, and the backfill refuses it.

**What it reads** (`read.mjs`; base `https://api.juo.io/admin/v1`, cursor paging `{ data, hasNextPage, endCursor }`, the next page with `after=<endCursor>`, at most 100 a page; the search query language on the list endpoints):

| Read | Request | Used by |
|---|---|---|
| every subscription | `GET /subscriptions?limit=100&expand=paymentMethod` | the reconcile, `--object subscription` |
| subscriptions by id | `GET /subscriptions?limit=100&expand=paymentMethod&query=(id:'<id>' OR …)`, 25 ids a query | the poll, for the subscriptions its events touched |
| events of a window | `GET /events?limit=100&sort=occurredAt:asc,id:asc&query=category:subscription AND occurredAt:>'<ISO>'[ AND occurredAt:<'<ISO>']` | the poll (after its cursor less five minutes), `--object subscription_event` (from `--from`, `>=`) |

The payment method is expanded for its instrument's type only. Juo's rate limit is not documented and no rate-limit header was seen on a GET (Open decisions). The paths, `expand=paymentMethod` and the query forms follow Juo's connector as read on 28 October 2026 (juo.dev was out of this session's reach); PROD_RUNBOOK 15.6's dry run confirms them on the live store: an answer other than 200 fails the run with `http_<status>`, and a subscription without its instrument's type counts as such (`instrumentKnown`).

**The event types** (Juo's `GET` event types, read on 28 October 2026). The CMA stores the events below, each in its own word (`subscription_event.event_type`), so no vendor's type word drives a figure; Juo's type stays in `raw.type`.

| Juo's type | `event_type` | What it carries into the row |
|---|---|---|
| `subscription:renewed` | `renewed` | `cycleIndex`; the order's id in `raw.orderId` |
| `subscription:renew-failed` (severity problem) | `renew_failed` | `cycleIndex`, `attempt`, `errorCode` (upper case), `reason` as a code; `errorMessage` is never read |
| `subscription:cancelled` (alias `subscription:canceled`) | `canceled` | `previousStatus` → `status_from`, `status_to` canceled; `reason` is the caller's free text: kept only as a code of the list below, else dropped and counted |
| `subscription:paused` | `paused` | `previousStatus` → `status_from`, `status_to` paused |
| `subscription:resumed` | `resumed` | `previousStatus` → `status_from`, `status_to` active |
| `subscription:reactivated` | `reactivated` | `previousStatus` → `status_from`, `status_to` active |
| `subscription:updated` whose data names a status | `status_changed` | `data.status` → `status_from`, `data.input.status` → `status_to` (Juo's own move to failed arrives so: ACTIVE → FAILED by the system); an update without a status, or with the same one, is no event of the CMA |

Every other event of a subscription (`subscription:created`, `:skipped`, `:discount-*`, `:line-*`, `:delivery-address-changed`, `:payment-method-changed`, `:next-billing-date-changed`, `:merged-to`, …) is read, its subscription is read again by the poll, and it is not stored (counted `skipped`). Statuses arrive in lower case on a subscription and in upper case in an event; the adapter writes the seven in lower case (`cancelled` as `canceled`, `NEVER_SUBSCRIBED` as `never-subscribed`). The reasons kept (`map.mjs` `REASON_CODES`): `billing-attempt-failed`. The actor: `staff`, `customer`, `system`, `bulk` (Juo's `bulk-action`), `api`; a staff actor's id only, never a name.

**The whitelist** (`map.mjs`): only the fields named here are read, so a subscription's delivery address, its customer's name, email and phone, the payment method's holder, account, card digits and billing address, custom attributes, items' titles, an event's actor name, an error message, a free-text reason and an update's input never reach a row, `raw`, a log or the database. A subscription: its id, the customer's id at the store (digits; from a gid too), the status, `currentCycle`, `nextBillingDate`, `billingPolicy.interval` (`day`, `week`, `month`, `year`) and `intervalCount`, the amount per cycle (the sum of the `totalPrice` of the items Juo has not canceled), `currencyCode`, the instrument's type (`card` when the type names a card, `paypal`, else `other`; none without the expanded payment method), `createdAt`, `pausedAt`, `canceledAt`, `updatedAt`. `raw` holds those values under Juo's names. The database checks `raw` again: its keys from a fixed list, scalar values, never an @ (`cma.subscription_raw_ok`).

**Settings** (connection settings, `cma.set_connection_settings`, which replaces the whole object, so merge the current ones in; or Configuration → Sources → the connection → Settings).

| Setting | What | Default |
|---|---|---|
| `juo_poll_interval_minutes` | how often the poll reads (1 to 60) | 5 |
| `juo_max_per_second` | the pace on the store's key, per connection and process (1 to 10) | 2 |

The database refuses either out of range on a subscriptions connection (CMA04); a value stored before out of range gives the default and one log line per run (`settings out of range, defaults used`, naming the setting).

**Pacing.** Every request waits for the connection's slot (`juo_max_per_second`). A 429 holds the connection until its `Retry-After` (seconds or a date, at most a minute; five seconds without one) and the same request is sent again once the hold has passed, at most twice: a third 429 fails the run `rate_limited`, the cursor stays, and the next run carries on (`juo rate limited` in the log, with the attempt and whether it was sent again). Every request is counted per endpoint (`GET /subscriptions`, `GET /events`, no query value) in the run's log line.

**Poll** (`ingest-poll-subscriptions`, every 5 minutes, Europe/Amsterdam; created paused). Per active Juo connection with a token secret name, when due on `juo_poll_interval_minutes` (cursor `juo:cadence`), one `sync_run` row (job `subscriptions_poll`, stream `subscriptions`): the store checked, the events that occurred after the cursor `juo:events` less five minutes (the last 24 hours when it has none; the events backfill sets it), stored as they come (`cma.ingest_upsert_subscription_events`: an event already held is left as it is, so the overlap stores nothing twice), then every subscription those events touched (whatever their type) read again by id and upserted; both cursors move to the run's start.

**Reconcile** (`ingest-reconcile`, 03:30). The full read: every subscription of the store, upserted page by page (`cma.ingest_upsert_subscriptions`: a stale guard on Juo's `updatedAt`; a subscription that comes back clears `source_deleted_at`), then the final step in slices of 1,000 ids (sorted by their bytes, `core/slices.mjs`, as the Airtable adapter's devices), each its own call of `cma.ingest_mark_subscriptions_missing(connection, ids, from, before)`: a subscription the read no longer returned gets `source_deleted_at`. A read that returns no subscription fails `empty_snapshot` instead of marking every subscription missing (`juo full read returned no subscription: nothing marked missing`); a run that fails before the final step marks nothing. One `sync_run` row (job `reconcile`, stream `subscription`).

**Backfill** (`ingest-backfill --connection <id> --object subscription [--dry-run]`, `--object subscription_event --from <date> [--dry-run]`). `subscription` is the reconcile's full read on demand, without `--from`. `subscription_event` reads the events from `--from` (00:00 in the tenant's zone; without it `intake.start_date`) to the run's start, oldest first, resumable (cursor `backfill:subscription_event`: the latest occurrence stored), a finished one with the same start reading nothing unless `--again`; at its end the poll's cursor `juo:events` moves to the run's start unless it stands later, so the poll carries on where the backfill ended. Run the events first, then the subscriptions: a paused subscription's `paused_at` comes from its pause event. With `--dry-run` either reads and counts and writes nothing (no upsert, no `sync_run` row, no cursor): one log line `backfill dry run` with, for `subscription`, `fetched`, `mapped`, `unreadable`, `statuses` (per status), `instrumentKnown`, `withoutCustomer` and `customersUnmatched` (customer ids the store's customers do not hold), and for `subscription_event`, `fetched`, `mapped`, `otherType`, `unreadable`, `eventTypes` (Juo's types seen, with counts), `kept` (per CMA type), `reasonDropped` and `customersUnmatched`.

**Counts** (`sync_run.counts`; `cma.ingest_sync_run_finish` takes them since 0008zl): `fetched` (events and subscriptions read), `inserted`, `updated`, `unchanged` and `stale` (subscriptions), `upserted` (inserted and updated), `events_new` (events stored for the first time), `skipped` (events of another type or unreadable, unreadable subscriptions), `customers_unmatched` (subscriptions written whose customer the store's customers do not hold), `reason_dropped` (a reason left out), `missing_now` and `slice_max_ms` (a full read's final step).

**Error codes**: `token_unavailable` (the key's secret cannot be read), `tenant_id_invalid` (the account id is not `<handle>.myshopify.com`), `store_not_configured`, `key_rejected` (401: a wrong key, or another store's), `rate_limited`, `empty_snapshot`, `from_not_set`, `too_many_pages`, `http_<status>`, `timeout`, `unreachable`, `bad_response`; the database's `db_CMA04` for an item out of its form.

**Data protection** (hard rules):
- Only the whitelisted fields are read; no name, email, phone, address, payment detail, message or free-text reason is stored, and a reason enters only as a code of the fixed list (the run counts the rest as `reason_dropped`, never the value).
- The database checks the subscription's and the event's ids (no space, no @) and `raw` (fixed keys, scalars, no @); 119's Z1 reads every row of both tables for an email pattern.
- Logs hold connection ids, counts, codes and Juo's type names only: never the key, a value, a customer's id or a payload.

**Logs.** Per connection one line `poll-subscriptions: connection` with the run's counts, the details (`eventsRead`, `eventsKept`, `eventsOtherType`, `eventsUnreadable`, `eventTypes`, `subscriptionsRead`, `subscriptionsUnreadable`, `instrumentKnown`, `touched`, `since`) and the requests per endpoint; the lines `reconcile: subscriptions` (with `slices`), `backfill: subscriptions`, `backfill: subscription events` and `backfill dry run`; the warnings `juo store not configured: …`, `juo rate limited` and `juo full read returned no subscription: nothing marked missing`; `poll-subscriptions: connection skipped` and `reconcile: connection skipped` (`key_not_set`).

**Verifiers:** `verify/juo-mapping.mjs` and `verify/juo-flow.mjs` (section Verifiers), both against the fake Juo `verify/juo-fake.mjs`; each fails every check when provoked. `db/119_verify_subscriptions.sql` proves the database's side.

## Outbox

The outbox worker (`ingest/src/jobs/outbox.mjs`, the job `ingest-outbox`; DESIGN §4.3a; migration 0007c) delivers CRM contact write-backs. **It is generic and, since 0008h, unused** (README Decision log, 13 October 2026): the CMA writes nothing back for a store's customers, so nothing enqueues an action, and `deploy.sh` deploys the job without a schedule (a schedule an earlier deploy made is paused). It stays for a write-back a later decision configures, with `verify/outbox-flow.mjs` proving it. Per CRM connection whose adapter writes contacts (HubSpot, `src/adapters/hubspot/write.mjs`): the due actions are claimed 50 at a time (`FOR UPDATE SKIP LOCKED`, never two of one contact), the contacts' current values of the enabled write-back properties are read in one batch read, each action is planned by mode, and the differences are written in one batch update:

- `always` writes when the value differs (`240` equals `240.00`); `if_empty` writes only into an empty property, so an agent's country, currency or language is never overwritten; `slot` (the customer id only) leaves the id where it already is, else fills slot 1, else slot 2, and writes nothing when both hold other ids (`slots_full`).
- The store and the two totals describe the customer in slot 1: written only when this customer's id is, or just became, slot 1.
- A property that is not an enabled write-back field of the connection is refused in code (`property_not_configured`), after the database already kept only enabled fields at the enqueue; a field disabled after the enqueue is not written.

Each action finishes as `sent` with its result (`written` and `skipped` properties with the reason, `ref` written, present or slots_full, and the `slot`), or `failed` with `rate_limited`, `timeout`, `http_<status>`, `contact_not_found` (the contact is gone from HubSpot) or `contact_rejected`; the claim set the next attempt already (1, 2, 4 … 60 minutes) and after `outbox.max_attempts` (8) the action is parked as `needs_review` for a person to retry or drop. The job reads and writes contact properties only; it never reads an email.

## API budget (backlog CMA-069)

Every app of a HubSpot portal shares the portal's daily limit (HubSpot, API usage guidelines: the burst limit is per app, the daily limit per account), Juo, the Shopify connection and the other private apps included. On 18 October 2026 the app CMA ingest prod made 173,444 calls in 24 hours, 17% of it, about 120 a minute with almost no webhooks: polling. Since then (`src/adapters/hubspot/usage.mjs`):

| What | How |
|---|---|
| Counted forms | read every minute, as before: speed to lead and Intake read only them |
| Polled-only forms | every `forms_poll_interval_minutes` (default 5): their slots follow the forms' order, so each minute of an interval holds an even share (22 forms: 5, 5, 4, 4, 4), and a run reads the slots of every minute since the previous run (cursor `forms:cadence`), so a minute skipped behind the job's lock only delays its share. A form's cursor reads every submission newer than its last read, so the cadence delays a submission by at most one interval and loses none. A form with nothing new costs one call |
| The probe | `forms_poll_probe` (default false, left off): one contacts search a minute for a `recent_conversion_date` since the last run that read every counted form, less two minutes for the search index (cursor `forms:probe`); without a conversion the counted forms wait for their own slots of the same cadence. A submission without an email address creates no contact and no conversion, so the search never sees it: it arrives at its form's slot. The nightly reconcile catches it if its slot never came |
| The nightly reconcile | the safety net under both cadences: every polled form's submissions of the last 26 hours (stream `form_submission`), besides the email engagements and inbox threads, read again; a submission the CMA holds is skipped without a contact search, one it does not hold is written as the poll writes it. Its run's `upserted` is what the polls missed: 0, or a handful that arrived while it ran (`PROD_RUNBOOK.md` 12.4) |
| Threads | the walk ends at its first page with nothing after its cursor, whatever paging HubSpot hands, so an idle minute costs one threads call |
| Open check | every `email_open_check_minutes` (default 15) from its own last start, so each connection keeps its own phase; its cursor (`email:open-check`) takes the start before anything is listed, so a check that fails waits for the next one |
| Measuring | every request counted per endpoint template (method and path, each id replaced by `{id}`, no query value). The log lines `poll-forms: connection`, `poll-email: connection`, `sweep: connection`, `reconcile: stream` (and `reconcile: stream paused`) and `backfill` carry `apiCalls`, `api` (per endpoint) and `daily` (`{ limit, remaining }` as HubSpot's last response stated it, or `not_received`). `sync_run`'s counts carry no request count: `cma.ingest_sync_run_finish()` takes fetched, upserted, stale, skipped, failed and dropped only, so a key such as `api_calls` is a later migration. The webhook route's own read-backs are not in these lines; HubSpot's Monitoring page counts everything |
| The daily floor | backfill and reconcile only: once the remaining daily calls fall below `api_daily_floor_pct` (default 25) of the limit, the next request is not sent and the run pauses. `sync_run` knows no skipped status, so the row is finished as succeeded with error `daily_floor` (System health shows it as OK with the code beside it), the log says `backfill paused` or `reconcile: stream paused`, and the job exits 0. A backfill continues from its cursor when run again; a reconcile stream starts the next night at the paused run's start (cursor `reconcile:<object>`, cleared once a run finishes). A poll and the sweep never pause: their budgets carry no floor |
| The headers | `X-HubSpot-RateLimit-Daily` and `X-HubSpot-RateLimit-Daily-Remaining`. HubSpot leaves them out of OAuth-authorized requests (no daily limit there); the CMA's app has a static token and private distribution, so it should receive them. HubSpot's published specs (`github.com/HubSpot/HubSpot-public-api-spec-collection`) declare no response headers, so only a live response shows it: `daily: "not_received"` in the run lines means they do not arrive, and the guard then never pauses. The guard is insurance: the portal is on Enterprise with ample daily headroom, so no database-side counter is built (README, Decision log, 18 October 2026) |

Every value out of range (not a whole number in its range, or a probe value other than true or false) gives the default, named in one log line per run (`settings out of range, defaults used`). Prod's steps: `PROD_RUNBOOK.md`, API budget (CMA-069).
