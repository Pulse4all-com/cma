How Joshua queries it

  • He needs BigQuery Connection User on the project that holds the connection, plus the right to run query jobs (BigQuery Job User)
  • Each query is passed to Postgres as plain SQL inside EXTERNAL_QUERY; the result can be joined with BigQuery tables
  • Every running query holds one database connection, five are reserved for BigQuery. For dashboards that refresh often, a scheduled query copying into an EU dataset is lighter
SELECT *
FROM EXTERNAL_QUERY(
  "p4a-cma-dev.europe-west4.cma_dev_read",
  """select business_date, market,
            deals_created, calls_in, first_orders
     from cma_read.intake_per_day_v
     where business_date >= current_date - 30""");

What BigQuery does not see

  • Raw source payloads, phone and caller hashes, tokens and secret names, the old and new values in the audit log: left out on purpose
  • The inbound service level and the calls overview (Reports, Inbound and Calls) exist only as Workspace functions; recomputing them from telephony_call risks different numbers
  • A Shopify customer's matched HubSpot contact is not in cma_read.commerce_customer; only lead_to_order uses it

Source of truth stays with the owning system: HubSpot for leads, deals and tickets, Aircall for call facts, Shopify for orders, Trusted Shops for reviews, the CMA for time, roster, people and messages. Postgres mirrors, it never overrules. Readers see both business lines unless their login is limited to one
