# CMA data map

One page, `index.html`, that shows every table in schema `cma`: what it holds, where it gets its data and how often, its columns, and which of them the readers (BigQuery, NocoDB) see through `cma_read`. Columns come from the database, never from a hand-written list; the descriptions and the paths the page draws are hand-written in one catalog that a verifier keeps complete.

## The files

| File | What it is | Who writes it |
|---|---|---|
| `catalog.json` | Groups (`key`, `label`, `tables` with `name`, `what`, `how`), the computed views of `cma_read` under `derived` (`name`, `what`) and the `flows` the page draws. `what` is what a table holds, `how` is which source fills it and how often | By hand, in the PR that changes a table, a view or a source |
| `schema.json` | The schema snapshot: `generated_at`, `latest_migration` and every column of `cma` and `cma_read` as `[schema, table, table_type, column, type]`, from `tools/datamap/schema.sql` | Generated from dev, never edited |
| `template.html` | The page: its boxes for sources, ways in and readers, and a script that reads `const DATA = __DATA__;` (the shape is in the comment above that line) | By hand |
| `index.html` | The page with its data filled in, committed | Generated by `tools/datamap/build.mjs`, never edited |

`tools/datamap/` holds `schema.sql` (the read-only snapshot query), `build.mjs` (writes `index.html`; `--check` builds in memory) and `verify.mjs` (`npm run verify:datamap` from `web/`, with `--provoke`). Plain Node 22, no dependencies.

The page's stamp is the snapshot's `generated_at`, so the same three files always build the same page.

## Flows

`flows` in `catalog.json` holds one entry per source: `{"src": ..., "ways": [...], "doms": [...]}`. `src` is the `data-id` of the source's box in `template.html` (`null` when it has none, as for the scheduler), `ways` the `data-id`s of its ways in, `doms` the group keys it fills. Selecting a box on the page lights the flows through it. A new source or way in needs its box in `template.html` as well as its flow; a new group needs to be in at least one flow.

## What the check refuses

`node tools/datamap/build.mjs --check` (and `npm run verify:datamap`) exits 1 and lists every problem when

- a table in `cma` has no catalog entry
- a catalog table is not a table in `cma`, or a `derived` entry not a view in `cma_read`, in `schema.json`
- a view in `cma_read` is none of: a view over a catalog table (same name), a `derived` entry, a `dq_` view
- a name appears twice in the catalog
- a catalog entry has no `what`, or a table no `how`
- a flow names a domain that is not a group key
- a group appears in no flow
- a flow's `src` or way is not a `data-id` in `template.html`
- `index.html` differs from a fresh build

`build.mjs` without `--check` refuses to write while any of these but the last holds. On success the check prints one line:

```
datamap: 66 tables, 82 views, all described; index.html current
```

## When it changes

- A PR that adds or changes a table, view or column in `cma` or `cma_read` updates `catalog.json`: a `what` and `how` for each new table, an entry under `derived` for each new computed view. Its description says that Martin refreshes `schema.json` from dev on that branch after running the migration there, before merging. Until then `verify:datamap` fails on that branch, naming the new table or view as missing from `schema.json`; that is expected.
- A change to how or how often a source fills a table (webhooks, job schedules, catalogs) updates that table's `how` in the same PR (and its flow, when the source fills another group or comes in another way), then `node tools/datamap/build.mjs` so `index.html` stays current.
- Martin refreshes the snapshot and rebuilds the map on the increment's branch, after its migration and verify ran in dev and before the merge (below), so main always passes `verify:datamap`.

Never put customer data in the catalog: describe what a table holds, never a value from it.

## Refreshing the snapshot

On the increment's branch in Cloud Shell (`gh pr checkout <number>` in `~/cma`), after its migration and verify ran in dev, through the Auth Proxy as in README (Working on the code).

**Terminal** (first tab; leave it running)

```bash
cloud-sql-proxy --auto-iam-authn --port 5433 p4a-cma-dev:europe-west4:cma-dev-pg
```

Expected: `The proxy has started successfully and is ready for new connections!`

**Terminal** (second tab, in `~/cma`)

```bash
psql "host=127.0.0.1 port=5433 dbname=cma user=$(gcloud config get-value account) sslmode=disable" -X -qAt -v ON_ERROR_STOP=1 -f tools/datamap/schema.sql > docs/datamap/schema.json
```

Expected: nothing printed; `docs/datamap/schema.json` is one line of JSON whose `latest_migration` is the increment's migration.

**Terminal** (`~/cma`)

```bash
node tools/datamap/build.mjs && node tools/datamap/build.mjs --check
```

Expected: `datamap: wrote docs/datamap/index.html (<n> tables, <m> views)`, then `datamap: <n> tables, <m> views, all described; index.html current`. A problem list instead names what the catalog lacks: add it to `catalog.json` and run both again.

**Terminal** (`~/cma`)

```bash
git add docs/datamap && git commit -m "Data map: snapshot after <migration>" && git push
```

Expected: the push names the increment's branch. The PR now passes `verify:datamap`; merge as usual.
