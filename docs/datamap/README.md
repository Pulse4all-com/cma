# CMA data map

One page, `index.html`, that shows every table in schema `cma`: what it holds, where it gets its data and how often, its columns, and which of them the readers (BigQuery, NocoDB) see through `cma_read`. Columns come from the database, never from a hand-written list; the descriptions are hand-written in one catalog that a verifier keeps complete.

## The files

| File | What it is | Who writes it |
|---|---|---|
| `catalog.json` | Groups (`key`, `label`, `sources`, `tables` with `name`, `what`, `how`) and the computed views of `cma_read` under `derived` (`name`, `what`). `what` is what a table holds, `how` is which source fills it and how often | By hand, in the PR that changes a table, a view or a source |
| `schema.json` | The schema snapshot: `generated_at`, `latest_migration` and every column of `cma` and `cma_read` as `[schema, table, table_type, column, type]`, from `tools/datamap/schema.sql` | Generated from dev, never edited |
| `template.html` | The page; its script reads `const DATA = __DATA__;` (the shape is in the comment above that line) | By hand |
| `index.html` | The page with its data filled in, committed | Generated by `tools/datamap/build.mjs`, never edited |

`tools/datamap/` holds `schema.sql` (the read-only snapshot query), `build.mjs` (writes `index.html`; `--check` builds in memory) and `verify.mjs` (`npm run verify:datamap` from `web/`, with `--provoke`). Plain Node 22, no dependencies.

The page's stamp is the snapshot's `generated_at`, so the same three files always build the same page.

## What the check refuses

`node tools/datamap/build.mjs --check` (and `npm run verify:datamap`) exits 1 and lists every problem when

- a table in `cma` has no catalog entry
- a catalog table is not a table in `cma`, or a `derived` entry not a view in `cma_read`, in `schema.json`
- a view in `cma_read` is none of: a view over a catalog table (same name), a `derived` entry, a `dq_` view
- a name appears twice in the catalog
- a catalog entry has no `what`, or a table no `how`
- `index.html` differs from a fresh build

`build.mjs` without `--check` refuses to write while any of these but the last holds. On success the check prints one line:

```
datamap: 66 tables, 82 views, all described; index.html current
```

## When it changes

- A PR that adds or changes a table, view or column in `cma` or `cma_read` updates `catalog.json`: a `what` and `how` for each new table, an entry under `derived` for each new computed view. Until the snapshot is refreshed, the check names the new table or view as missing from `schema.json`; that is expected and said in the PR.
- A change to how or how often a source fills a table (webhooks, job schedules, catalogs) updates that table's `how` in the same PR, then `node tools/datamap/build.mjs` so `index.html` stays current.
- After a migration's verify in dev, Martin refreshes the snapshot and rebuilds the map in the increment's records PR (below).

Never put customer data in the catalog: describe what a table holds, never a value from it.

## Refreshing the snapshot

From a clone in Cloud Shell, through the Auth Proxy as in README (Working on the code), against dev.

**Terminal** (first tab; leave it running)

```bash
cloud-sql-proxy --auto-iam-authn --port 5433 p4a-cma-dev:europe-west4:cma-dev-pg
```

Expected: `The proxy has started successfully and is ready for new connections!`

**Terminal** (second tab, in `~/cma`)

```bash
psql "host=127.0.0.1 port=5433 dbname=cma user=$(gcloud config get-value account) sslmode=disable" -v ON_ERROR_STOP=1 -qAt -f tools/datamap/schema.sql > docs/datamap/schema.json
```

Expected: nothing printed; `docs/datamap/schema.json` is one line of JSON whose `latest_migration` is the migration just run in dev.

**Terminal** (`~/cma`)

```bash
node tools/datamap/build.mjs && node tools/datamap/build.mjs --check
```

Expected: `datamap: wrote docs/datamap/index.html (<n> tables, <m> views)`, then `datamap: <n> tables, <m> views, all described; index.html current`. A problem list instead names what the catalog lacks: add it to `catalog.json` and run both again. Commit `schema.json` and `index.html` (and `catalog.json` if it changed) in the records PR.
